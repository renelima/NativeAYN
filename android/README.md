# nxnative no Android

O porte do host para Android: um único APK de launcher (`android/app`) que contém o host, um por jogo que ele executa (`libnxhost_<title ID>.so`, compilado de `android/host`), e nenhum código de jogo, e um pack por jogo, feito a partir do dump do próprio usuário: pelo próprio app no celular (**Prepare**, ONDEVICE.md) ou no Mac e copiado para o celular ao lado da pasta do jogo. Esta build inicializa o lado de CPU de um jogo e reproduz seus clears, cópias e presents de NVN em Vulkan (os draws ainda não estão em Vulkan), toca seu som por AAudio, decodifica seus vídeos com `AMediaCodec` e aceita gamepads, toques e o movimento do celular; um autoteste gráfico verifica o caminho Vulkan sem um jogo. [PORTING.md](PORTING.md) traz o projeto, o estado atual e as próximas peças; [TESTING.md](TESTING.md), os passos no celular. [FRONTENDS.md](FRONTENDS.md) explica como launchers e frontends de jogos (ES-DE, Daijisho, Pegasus…) iniciam um jogo.

| Pasta | O quê |
|---|---|
| `android/host` | build CMake de `libnxhost.so` para arm64-v8a, API 33+ (`GAME=<title ID>` escolhe o profile; `NX_GAMES=<id>,<id>,…` compila `libnxhost_<id>.so` para cada, como o APK faz) |
| `android/app` | o launcher: Gradle + CMake, Java, `dev.ankanative.android.test`, com o nome "NativeAYN test" (`-PnxPlay=true`: `dev.ankanative.android.play`, "NativeAYN"; `-PnxApp=oot`: `dev.ankanative.android.oot`, "NativeAYN"; `-PnxLive=true`: `dev.ankanative.android`) |
| `scripts/pack_android.py` | o empacotador (o do Mac, e o do próprio app: as mesmas ferramentas rodam dentro do app, ONDEVICE.md) |
| `android/ondevice` | o empacotador do app, lado nativo: CPython embutido (`libnxpack.so`), e `build.sh`, que gera o stage que o APK incorpora |

**Licença.** O nxnative é MIT. A build do Android inclui a geração de frames do Lossless Scaling, portada do Eden ([`dm/gfx/vk_android/lsfg`](../dm/gfx/vk_android/lsfg/LICENSE.md)), que é GPL-3.0-or-later: **um APK compilado com ela (o padrão) é GPL-3.0-or-later como um todo**; `-PnxLsfg=false` compila um sem ela. Veja [NOTICE.md](NOTICE.md). `Lossless.dll` nunca está no repositório nem no APK.

## O ambiente

Preparar um jogo em um computador funciona no Windows, no Linux e no Mac. São necessários:

- **Python 3.14** com Capstone 5, lz4 e zbic (`pyproject.toml`, grupo de dependências `android-pack`; zbic lê o código comprimido em zstd dos
  system 22.0.0+ como Ocarina of Time).
- O **runtime do .NET 10**, que executa o tradutor de shaders commitado (`dm/gfx/tools/dmsh_xlate_bin`). No Mac ele inicia como `dmsh_xlate`; no Linux e no
  Windows, `pack_android.py` o inicia pelo launcher que fica ao lado dele, `dmsh_xlate-<linux|win>-<x64|arm64>`.
- **spirv-val** (SPIRV-Tools) no `PATH`.

Mantenha o ambiente no drive do dump, não na pasta pessoal.

Windows (PowerShell; Python do python.org, .NET de https://dotnet.microsoft.com/download/dotnet/10.0, spirv-val do Vulkan SDK em
https://vulkan.lunarg.com, cujo instalador põe a pasta `Bin` no `PATH`):

```powershell
py -3.14 -m venv D:\Switch2\.venv-anka
D:\Switch2\.venv-anka\Scripts\python -m pip install "capstone>=5,<6" lz4 zbic
```

Linux (os pacotes `dotnet-runtime-10.0` e `spirv-tools` da distribuição; Python 3.14 da distribuição ou micromamba):

```sh
python3.14 -m venv <dump folder>/.venv-anka
<dump folder>/.venv-anka/bin/python -m pip install "capstone>=5,<6" lz4 zbic
```

No Mac (`brew install --cask dotnet-sdk`, `brew install spirv-tools`):

```sh
micromamba create -p <dump folder>/.venv-anka python=3.14 -c conda-forge
<dump folder>/.venv-anka/bin/python -m pip install "capstone>=5,<6" lz4 zbic
```

O Capstone vem do pip: o Capstone 5 do conda-forge encontra sua biblioteca só através de `CONDA_PREFIX`, então falha quando o Python do ambiente é executado sem ativá-lo.
No Windows, `pack_android.py` roda as ferramentas em modo UTF-8 (`PYTHONUTF8=1`; defina-o você mesmo para rodar uma delas diretamente), escreve todo arquivo de texto com finais de linha LF (`scripts/lf_newlines.py`), como o celular os lê, e reescreve o código em um único
processo (o Windows não tem `fork`); o próprio checkout também precisa ter finais de linha LF (as versões dos shaders e a chave de reescrita do código fazem hash dos arquivos do repositório), o que o `.gitattributes`
pede ao git: uma cópia clonada no Windows antes dessa regra, ou baixada como zip e descompactada por uma ferramenta que muda os finais de linha, deve ser clonada de novo.

## Preparar o pack de um jogo

```sh
<dump folder>/.venv-anka/bin/python scripts/pack_android.py <dump folder>/<game folder or .nup>
```

No Windows: `D:\Switch2\.venv-anka\Scripts\python scripts\pack_android.py "D:\Switch2\<game>.nup"`.

A pasta do jogo tem o layout que `scripts/pack_dump.py` lê (`base/exefs`, `base/romfs`, `updates/<version>/`, `dlc/<DLC title ID>/<n>/romfs`), e o jogo precisa de um profile em `dm/games`. O empacotador reescreve os modules do profile da versão mais recente (`--version N` para outra) com `patch_nso.py --target android` em `<game folder>/../<title ID>-work/android-pack/` (`--out` para outra pasta) e deixa o RomFS de fora. Uma nova execução mantém os modules cujas entradas não mudaram.

Ele também coloca a biblioteca de shaders do jogo no pack ([SHADERS.md](SHADERS.md)): a biblioteca da versão desta árvore de código, `v-<DMSH_VK_CHAIN>` (`dm/gfx/nvn/dmsh_chain_vk.h`). Uma que esteja no cache de shaders, `<title ID>-work/android-shaders/lib/v-<V>/` (`--shader-cache` para outra pasta de bibliotecas `v-<V>/`), é copiada quando o seu `inputs.tsv` nomeia este jogo e os inputs atuais do profile dele; caso contrário, o empacotador a constrói ali a partir do pacote de shaders do Switch, `<title ID>-work/android-shaders/pkg` (`--shader-pkg`; a saída de `shader_split.py`, a pasta que `dmsh_build.py` recebe), com `vk_android_build.py` (uns 10 minutos para DKB com `-J 12`). A compilação precisa de Python 3.14 (ou `backports.zstd`), do runtime do .NET 10 e do `spirv-val`; o empacotador a roda como subprocess com o primeiro de `python3.14` / `python3` que tiver zstd (`--shader-python` nomeia outro). Sem biblioteca nem pacote, o pack é feito sem shaders e uma linha `[RED]` diz isso; `--no-shaders` os deixa de fora de propósito. Bibliotecas de outras versões em `shaders/` do pack são mantidas (outro APK pode carregar uma; apague-as à mão para economizar espaço). Cada module é reescrito em `<pack>/.rewrite-<module>/` e movido para dentro quando completo, com o seu `<module>.android.key` por último: um module sem a sua chave está incompleto, e o launcher o recusa. A chave faz hash dos arquivos do rewriter (`REWRITER`), do module, do `patches.py` do profile e das linhas `build` do `game.tsv` (as únicas linhas que o rewriter lê; uma chave antiga feita com o `game.tsv` inteiro ainda vale quando a própria cópia do pack tem as mesmas linhas `build`: [packing.md](../docs/reference/packing.md)); uma chave feita com um arquivo de rewriter anterior, guardado em `dm/tools/rewriter_equiv/<file>.<commit>`, conta como atual, tanto para o empacotador (o module é mantido) quanto para o launcher (`RewriteKey`, sem o chip "other tools"). Um arquivo só vai para lá quando a saída da reescrita com ele foi verificada como byte-idêntica à do arquivo atual em cada jogo (`patch_nso.py.b4269ab15768`: 10767b45 só limpa o cache de decodificação da busca de spin por head; MKW e DKB main idênticos). Testes: `dm/tools/tests/test_android_rewritekey.py`.

| Arquivo no pack | O quê |
|---|---|
| `<module>.patched.bin`, `.fixups.tsv`, `.gates.tsv`, `.sites.tsv`, `.changed.tsv`, `.cuts.tsv`, `.obs.tsv` | o module reescrito e as suas tabelas, como o host do Mac os carrega (`fixups.tsv` diz `TARGET_ANDROID 1`) |
| `pack.tsv` | formato, title ID, nome, versão, modules e seus build IDs, a pasta do RomFS e a pasta de cada DLC em relação à pasta do jogo, `shaders` (o caminho da biblioteca no pack, quando há uma), o commit do empacotador |
| `shaders/v-<DMSH_VK_CHAIN>/dmsh_vk.lib`, `inputs.tsv` | a biblioteca de shaders para o replay em Vulkan (SPIR-V, zstd; uns 350 MB para DKB) e o seu carimbo (inputs do jogo e do profile) |
| `game.tsv` | o profile (o host o tem compilado dentro; mantido para referência) |
| `rewrite_<module>.log`, `<module>.android.key`, `build_src.sha256` | a saída do rewriter e o que uma nova execução compara |

Os packs são feitos dos dumps do próprio usuário para o celular do próprio usuário: nunca vão para o repositório nem para lugar público nenhum.

## Compilar o APK

```sh
android/ondevice/build.sh <work dir>                                   # uma vez (e depois de uma mudança em dm_pack.c, no tradutor ou nos pins): <work dir>/stage
cd android/app && ./gradlew -PnxPackStage=<work dir>/stage apk         # → android/app/out/anka-native-test.apk
```

Todo APK leva o empacotador que prepara um jogo no celular (ONDEVICE.md, In the APK): CPython 3.14 e as ferramentas do repositório, o tradutor e o SPIRV-Tools; `-PnxPackStage` (ou `NX_PACK_STAGE` no ambiente) nomeia o stage que `android/ondevice/build.sh` gera, e o Gradle para e diz o que rodar sem ele. `-PnxPackEngine=fake` compila um empacotador simulado em vez disso, para trabalho nas telas (os packs dele são marcadores de posição que nunca iniciam). Tamanho (2026-11-03): 23,8 MB, dos quais o empacotador ocupa 20,9 MB (`libpython3.14.so` 5,8, `python.zip` 6,0, `libdmsh_xlate.so` 4,2, SPIRV-Tools 2,75, `tools.zip` 2,1, `libnxpack.so` 0,01, todos stored); sem ele o APK tinha 2,8 MB.

**Jogos no APK.** O host tem o profile do jogo compilado dentro (`game_profile.h`, como o `GAME` do `dm/host/Makefile`), então o APK leva um host por jogo: `-PnxGames=<title ID>,<title ID>,…` (padrão `nxGame` em `gradle.properties`, `040074A01BF12000`, Donkey Kong Bananza) compila `libnxhost_<title ID>.so` e o seu shim JNI `libnxlaunch_<title ID>.so` para cada (`android/app/src/main/cpp/CMakeLists.txt`, `nxhost_add` em `android/host/CMakeLists.txt`), coloca cada profile no `tools.zip` do empacotador, e entrega ao launcher o nome, as builds, a contagem de shaders e o digest dos inputs dos shaders de cada jogo (`BuildConfig.NX_PROFILES`, lido por `Profile.java`). O processo do jogo carrega só o seu próprio par (`Native.load`); o autoteste carrega o do primeiro jogo. Cada jogo adicionado compila o host mais uma vez (mais ou menos o mesmo tempo de novo). Um jogo cujo profile não está no APK é recusado com uma frase (`Profile.missing`), quando é adicionado, preparado ou iniciado; nada quebra. Um profile provisório feito pelo script do NSP no Mac (`DM_GAMES_DIR`) não está em `dm/games`, então ainda não dá para compilar um APK com ele. `-PnxApp=<suffix>` faz dele outro app de teste, `dev.nxnative.android.<suffix>` (rótulo `NativeAYN <suffix>`, ou `-PnxLabel=`), em `out/anka-native-<suffix>.apk`: um jogo em bring-up (`-PnxGames=0400C3F00006E000 -PnxApp=mkw`) instala ao lado do app de teste sem substituí-lo. O env.txt, os logs, os saves e os packs dele ficam em `/sdcard/Android/data/dev.nxnative.android.<suffix>/files/`; `-PnxPlay=true` compila o app de jogo (`dev.ankanative.android.play`). O APK é assinado com a chave de debug, debuggable, minSdk 33, só arm64-v8a, e as bibliotecas nativas ficam armazenadas sem compressão e alinhadas para páginas de 16 KB. O Gradle precisa de `android/app/local.properties` com `sdk.dir=` (o Android Studio o escreve) e do NDK 28.2.13676358.

## O launcher

- **Ícone e fundo**: o ícone é a marca Anka, uma fênix subindo (a mesma marca do projeto Anka, do mesmo autor; sem arte de jogo), desenhada por `android/tools/anka_logo.py` e escrita nos recursos por `android/tools/anka_icons.py`: um ícone adaptativo (`mipmap-anydpi-v26/ic_launcher` e `ic_launcher_round`: o gradiente escuro quente do azulejo, `drawable/ic_launcher_tile.xml`, atrás, a marca `drawable-<density>/anka_fg.png` na frente dentro da zona segura, e a sua silhueta branca `anka_mono.png` para ícones temáticos; `drawable/ic_launcher` e os PNGs `mipmap-<density>` são os legados). A marca dentro do app (o cabeçalho da Home, a lista de jogos vazia) é `drawable-nodpi/anka_mark.png`, o ícone de notificação é `anka_notify.png`. O ícone do app de teste tem um ponto "T" vermelho-laranja no canto inferior direito, o do app de jogo não tem: `build.gradle` acrescenta `src/variant-test/res` ou, com `-PnxPlay=true`, `src/variant-play/res`, que contêm `ic_launcher_badge*.xml`. Atrás da tela principal, `BananaBackgroundView` (a classe mantém o nome original) mosaica a mesma marca, apagada, numa grade diagonal inclinada que deriva devagar e se repete sem emenda; ela anima (Choreographer, no máximo umas 60 repinturas por segundo) só enquanto a tela principal está retomada, então nunca enquanto um jogo roda, e fica parada quando as animações do sistema estão desligadas (escala de duração de animação 0).
- **Duas páginas** (`MainActivity`): **Home**, o caminho para jogar, e **Configurações** (a engrenagem no cabeçalho da Home; Voltar retorna): Atualizações (primeiro), os padrões de todo jogo (overlay, resolução, limite de taxa de quadros, geração de frames), driver de GPU, Pastas, a Verificação de prontidão, o autoteste gráfico, Compartilhar log, e Sobre (a tag da build, os title IDs do APK, créditos). A Home mostra o cartão de Acesso a todos os arquivos enquanto ele estiver faltando, o jogo sendo preparado, e os jogos; sem nenhum, um cartão com os três passos (escolher dump, preparar, jogar) e **Adicionar jogo**. Um dump de um title para o qual o APK não tem profile é recusado com o title ID dele e os title IDs que este app executa (`Profile.missing`). O launcher não acrescenta nomes de jogo próprios: um jogo mostra o nome que o pack dele carrega, e a Verificação de prontidão mostra o nome do jogo adicionado ou o title ID dele.
- **Atualizações** (`Updater`, `UpdateCheck`; só o app de lançamento `dev.ankanative.android`): uma vez por início do app (um processo novo, `MainActivity.onCreate`; não num retorno de segundo plano nem numa rotação), a Home lê `https://api.github.com/renelima/NativeAYN/releases?per_page=10` (a lista: todo lançamento é um pré-lançamento, que o `/releases/latest` ignora; sem token, User-Agent `NativeAYN-updater`), pula rascunhos e tags que não são `vX.Y.Z`, e pega a versão mais alta acima do `versionName` do app que tenha um asset `.apk`. Um pop-up mostra a versão, as notas do lançamento (o Markdown do corpo do lançamento como texto estilizado: títulos, negrito, itálico, código, listas, links; `ReleaseNotes`; com rolagem quando longo) e o tamanho, com **Atualizar** e **Depois**; ele volta a cada início novo enquanto existir um lançamento mais novo. Atualizar baixa o asset pela `browser_download_url` própria (então o GitHub conta o download; nada é espelhado) para o `updates/` do cache com um diálogo de progresso, verifica o tamanho e, quando a API der um `digest`, o SHA-256 (um arquivo que falhar é apagado, nunca instalado), e instala com o `PackageInstaller` (uma sessão; o Android pede ao usuário que confirme). Quando instalações deste app não estão permitidas, o launcher abre a tela de **Instalar apps desconhecidos** do Android e continua ao voltar. Downloads antigos são apagados no próximo início. Uma verificação que falha (sem rede, limite de requisições, uma resposta ilegível) não mostra nada; a tag do logcat `nxupdate` diz o porquê. Configurações › **Atualizações**, a primeira seção: **Verificar atualizações** (a linha mostra `NativeAYN <version>`) verifica na hora: o pop-up, ou "Você está atualizado (vX.Y.Z)". Não há chave: o app de lançamento sempre verifica num início novo. Os apps de teste não verificam, a menos que `Android/data/<app>/files/update.txt` tenha `repo=<owner/name>` ou `url=<URL https de uma lista de lançamentos no JSON da API>`, com `version=<X.Y.Z>` para a versão que o app toma como sua (o `versionName` de um app de teste não é uma). Testes: `python3 dm/tools/tests/test_android_update.py` (`UpdateCheckJvmTest`: versões, escolha de lançamento, digests, o Markdown das notas, também no corpo real do v0.1.3).
- **Lista de jogos** (`MainActivity`): todo jogo adicionado tem um cartão (a inicial dele, nome, um estado: Pronto, Shaders necessários, Precisa preparar, …, um botão grande e ⋯ Gerenciar: uma lista com Configurações do jogo, Pastas, Backup / Restaurar / Importar saves, Preparar de novo, Exportar pack… / Importar pack…, Compartilhar log, e depois o title ID e as pastas, e Remover à parte embaixo); o botão é **Jogar**, ou **Preparar** / **Preparar shaders** quando o pack não serve e a pasta é um dump (ele vai direto para Preparar, que pergunta antes). **Adicionar jogo** abre o seletor do Storage Access Framework para uma pasta de jogo (um dump de qualquer jogo para o qual o APK tenha profile: `base/`, `updates/`), um `.nup`, ou uma pasta que contenha jogos: então todo jogo nela é adicionado (cada `.nup` nela e cada subpasta de dump com `base/exefs/main.npdm` ou `exefs/main.npdm`, um nível de profundidade; não `<title ID>-work` nem pastas de pack; `PackFind.gamesIn`), identificado fora da main thread, e uma mensagem diz o que foi adicionado, o que este app não pode executar (sem profile neste APK) e o que precisa de Preparar; uma pasta com um só jogo é esse jogo. O pack é procurado (`PackFind`, `Folders.find`) na pasta de pack escolhida para aquele title (Pastas), no armazenamento do app (`Android/data/<app>/files/packs/<title ID>`, onde Preparar e Importar pack… o colocam), ao lado e dentro do jogo como antes (`<game folder>/../<title ID>-work/android-pack`), depois na pasta que contém o jogo e até três pastas acima, nunca acima da raiz do volume de armazenamento: todo `<dir>/<title ID>-work/<qualquer nome>/` com um `pack.tsv` (um pack do Mac copiado como `xlate2-pack`, `android-pack-1.8.0`, …) e `<dir>/android-pack`. Só contam packs deste title cujo código serve para o jogo (`PackCheck.blocking`: a build do jogo do dump, uma build que este APK suporta, código terminado): primeiro um com a biblioteca de shaders deste APK, senão um cuja biblioteca mais antiga o restamp automático ou a atualização delta de shaders traga para a atual (o cartão então roda isso, como depois de uma atualização do APK); dentro de cada grupo, a pasta escolhida, depois a do app, depois a mais próxima. Um pack assim é usado sem pergunta. Um dump sem nenhum vai para **Preparar** (um job por vez, para qualquer jogo do APK): o app faz o pack no celular, ou só o que não serve (ONDEVICE.md, The app); a pergunta dele também oferece **Usar um pack existente…** (o seletor de pastas) e **Importar pack…** (um `.zip` do Exportar pack… ou uma pasta de pack). Num grupo de jogos, um dump sem pack utilizável ganha um cartão cujo botão é Preparar em vez disso (nenhum job começa sozinho). Uma pasta de versão única (`exefs/`, `romfs/`) sem pack ganha o seletor de pasta de pack. O estado de um cartão de jogo diz Pronto ou o que está errado; um pequeno chip **Pack de outras ferramentas** quando o código do pack foi feito por outras ferramentas que não as do APK, e um toque nele diz o que isso significa (normalmente funciona; ⋯ › **Preparar de novo** o atualiza). As árvores escolhidas são convertidas em caminhos `/storage/...` (`PathUtil`: `primary:` é o armazenamento compartilhado, outro ID de volume é `/storage/<ID>`), já que o host abre arquivos por caminho com o Acesso a todos os arquivos (`MANAGE_EXTERNAL_STORAGE`; a Home mostra um cartão com **Permitir** enquanto ele estiver faltando). Os jogos ficam lembrados nas preferências do app. Configurações › **Compartilhar log** envia o log mais recente, de um jogo ou do autoteste; o Gerenciar de um jogo tem o **Compartilhar log** próprio (o log mais recente daquele jogo). Configurações › **Autoteste gráfico** abre o `SelftestActivity` (TESTING.md, Test 2).
- **Uma execução** (`GameActivity`, no processo próprio `:game`): o host é iniciado uma vez por processo e termina esse processo. `nxhost_main("nxhost", <pack folder>)` roda numa thread nativa com uma pilha de 8 MB que o ART não conhece, com `DM_ROMFS=<game folder>/<romfs do pack.tsv>`, `DM_SAVE`, `DM_TEMP` (`<external files>/temp/<title ID>`: o cache de pipelines do jogo `vk_pipelines*.bin`, a lista de prewarm dele `vk_pipelines.keys` e os saves temporários do host, para que os jogos nunca os compartilhem), `DM_ROOT` e `DM_AOC_DIR` (`aoc/<title ID>`, links simbólicos para as pastas de DLC) na pasta de arquivos externos do app, depois as linhas de `<external files>/env.txt` (`KEY=VALUE`, para chaves de diagnóstico, todo jogo), as linhas do próprio jogo (Configurações do jogo), e `<external files>/env-<title ID>.txt` (o mesmo para um só jogo; as linhas posteriores vencem). Nenhuma delas pode definir os caminhos acima ou `HOME` (recusado com uma mensagem e uma linha `[RED]`; o app de teste pega `DM_SAVE` de `env-<title ID>.txt` para execuções de teste: [TESTING.md](TESTING.md#diagnostic-switches)). Um início que falha termina o processo `:game`. O stdout e o stderr do host vão para `<external files>/logs/<title ID>-<time>.log` (os 10 mais recentes de cada jogo são mantidos), e cada linha também vai para o logcat com a tag `nxnative`. Voltar pergunta antes de terminar o jogo.
- **Armazenamento do app** (`AppStorage`, como a pasta de usuário do Eden): `Android/data/<app>/files/` contém os saves (`saves/<title ID>`, `saves/<title ID>_device`) e os packs que Preparar gera ou Importar pack… recebe (`packs/<title ID>/`). Cada app tem o seu próprio; o Android o remove junto com o app, e `android:hasFragileUserData` faz a desinstalação perguntar se deve mantê-lo. O host recebe caminhos simples (`DM_SAVE`, a pasta do pack) como antes.
- **Saves** (`DM_SAVE`): a pasta escolhida nos Pastas do jogo, senão o `saves/<title ID>` do app. Um save de uma versão anterior no padrão antigo ao lado do jogo (`<Switch2 root>/saves/<title ID>` para o app de jogo e o de lançamento, `saves-test/<title ID>` para o app de teste; a raiz é a pasta que contém a pasta do jogo ou o `.nup`) é copiado uma vez no início do jogo quando o save do app está vazio: conferido arquivo por arquivo, sob as travas dos dois saves, nunca sobre um save do app, a pasta antiga nunca alterada; quando falha, aquela execução joga a pasta antiga e avisa (`SaveMigrate`). Um save vazio é então preenchido a partir do save privado das primeiras versões, senão de `<Switch2 root>/save-seed/<title ID>`; o log diz qual (`[nxlaunch] save: <path> (migrated|seeded|existing|new)`, e `copied once from …`). Pastas diz onde o save está. Veja [TESTING.md](TESTING.md#saves).

Recusado enquanto um jogo roda. O app nunca apaga um backup.

Uma linha `DM_NVN_GPU_TS` no `env.txt` ou nas linhas do próprio jogo vence ([a chave](../dm/games/README.md#chaves)); Donkey Kong Bananza: [Open](../dm/games/040074A01BF12000/README.md#em-aberto)).
- **Pastas…** (`Folders`, a folha Gerenciar de um jogo, ou Configurações › Pastas, que pergunta de qual jogo): a pasta daquele jogo, a pasta de pack dele (`pack.tsv` e `shaders/`) e a pasta de save dele, cada uma escolhida com o seletor de pastas e mantida por title ID nas preferências do app, então uma atualização do APK as mantém. Sem definir, valem os padrões acima. Uma pasta de pack escolhida vale para as futuras escolhas de jogo daquele title; uma pasta de save escolhida vai para o host como `DM_SAVE` exatamente como está (`[nxlaunch] save: <path> (chosen)`), nunca migrada para dentro nem semeada; quando está vazia e a pasta de save atual tem um save, o launcher pergunta antes de copiar (a cópia nunca sobrescreve, nada é apagado).

Tudo é guardado por forma de tela (o tamanho da view em passos de 40 unidades: `20x9` é a tela externa do PNM-N49, `20x18` a interna), então um dobrável mantém um layout por tela e um dobra/desdobra alterna entre eles; um grupo é guardado como um deslocamento em unidades e uma escala em torno de onde o layout automático o põe, então um layout salvo acompanha pequenas mudanças de tamanho e fica dentro da view. As prefs `touch_controls`: `group<g>@<shape>` = `dx dy scale`, `picture@<shape>` = `x y`. `TouchControls.layoutRows(ctx, box)`, `startEditLayout()` (roda `onEditStart` primeiro, que o painel dentro do jogo define como o fechar dele), `picturePosition()` / `setPicturePosition(y)` são o que uma página de configurações chama.

- **Overlay** (`GameActivity`, `Overlay`, ligado por padrão): no canto superior esquerdo uma pequena tag da build, no canto superior direito a taxa de quadros e o que o celular está fazendo, no canto inferior esquerdo as últimas linhas do log enquanto ele aparece (até o primeiro frame, depois de uma quebra, ou com Mostrar log ligado): tudo num tamanho só, 8 sp, branco numa pílula escura discreta com espaçamento apertado, encostada nos cantos e livre dos botões de toque ali; o bloco do log cresce no máximo até a borda inferior da tag. A tag da build é `NativeAYN 0.1 · <commit>` no app de jogo e `NativeAYN test · <branch sem "android-">@<commit>` no app de teste (sem hora da build: o commit e a digital da assinatura identificam uma build) (`+dirty` depois do commit quando a árvore tinha mudanças; o Gradle lê o git na hora da build, `unknown` sem ele); a mesma linha está em Configurações › Sobre e é a primeira linha de todo log de jogo, `[nxlaunch] build …`; a Home mostra só o identificador da build abaixo do título (`launcher-2@4a15067`, `1.0 · <commit>`: `Signer.buildId`, de que a tag é feita, então as duas nunca divergem). No canto superior direito, um item curto por linha para que o bloco caiba na barra preta ao lado da imagem 16:9 do jogo num celular largo (fora do HUD do jogo): um **ponto de throttle** e os frames por segundo do jogo (com geração de frames ligada, `<game>→<presented> fps` e `LSFG`), o tempo de frame, o tempo ocupado da GPU por frame (`GPU <ms>`, os timestamps das submissions médios nos últimos 32 frames cujo tempo entrou), os tetos de clock da CPU (`CPU 2.5/3.6` então `1.9/4.6 GHz`: o `scaling_max_freq` / `cpuinfo_max_freq` de cada cluster de cpufreq, cluster principal primeiro), a bateria (`41°C 87%`, `⚡` enquanto na tomada) e a memória: `App 4.3 GiB`, o conjunto residente do processo do jogo (VmRSS em `/proc/self/status`, páginas compartilhadas contadas inteiras; não PSS, que o `Debug.getPss` percorre cada mapeamento para calcular), depois `RAM 9.8/14.7 GiB`, a usada / total do celular (ActivityManager.MemoryInfo `totalMem - availMem` / `totalMem`, GiB como o `ram_gib` da verificação de prontidão), com um `low` vermelho enquanto o `lowMemory` do Android estiver marcado (`MemText`; lido numa thread própria, `overlay-mem`). O ponto é vermelho para status térmico MODERATE ou pior (`PowerManager.getCurrentThermalStatus()` ≥ 2), folga térmica ≥ 1,0 (`getThermalHeadroom(10)`, SEVERE) ou o cluster principal (a política com mais núcleos) limitado abaixo de 65 % do seu clock máximo; amarelo para status LIGHT, folga ≥ 0,85 (o PNM-N49 lê 0,69-0,75 com clocks no máximo) ou um teto abaixo de 85 %; verde caso contrário (cinza: nada legível). No PNM-N49 o jogo se mantém a 30 fps com cpu0-5 a 2,5 GHz de 3,63 (69 %, amarelo, o teto que o celular mantém mesmo frio) e cai para 20 fps nos tetos de 2,0-2,23 GHz (55-61 %, vermelho) que ele põe depois de esquentar, enquanto o status térmico ainda lê 1. O log recebe `[overlay] throttle <colour>: …` com as leituras quando a cor muda (no máximo a cada 10 s). Tudo isso são `TextView`s do Android sobre o `SurfaceView`, atualizados duas vezes por segundo (`nxhost_fps` de `vka_fps.c`; folga, bateria e memória a cada 2 s), sem trabalho de GPU, e nada é lido enquanto o overlay está desligado. Configurações: uma chave mestra e uma chave por item (tag da build, taxa de quadros, ponto de throttle, tempo de GPU, tetos de CPU, bateria, memória), todas ligadas por padrão (tela principal: as caixas de seleção e **Itens do overlay…**; no jogo: o painel dentro do jogo); `DM_OVERLAY=0` / `1` no `env.txt` sobrepõe a chave mestra para uma execução. O log também recebe `[vk] fps: …` a cada 15 s.
- **Selo de build oficial** (`Signer`, `Prefs.signers`): os apps de jogo e de lançamento terminam a tag da build com `· official` quando o certificado de assinatura do próprio APK (PackageManager `GET_SIGNING_CERTIFICATES`, os signers atuais) tem o SHA-256 da chave de lançamento (`Signer.OFFICIAL`: não definido até a chave de lançamento do dono existir, então até então toda build diz unofficial; [docs/RELEASING.md](../docs/RELEASING.md)) e é o único signer, senão `· unofficial build`; o app de teste não faz alegação nenhuma. A primeira linha do log do jogo (`[nxlaunch] build … · signer <16 hex>`) e o relatório de prontidão (`Signer:`) trazem os 16 primeiros dígitos hex do SHA-256 do signer, então um relatório de bug mostra qual chave o assinou. É uma conveniência, não uma prova: um app modificado pode imprimir qualquer texto; o que um usuário verifica é o certificado (`apksigner verify --print-certs <apk>`). Testado na JVM por `dm/tools/tests/test_android_signer.py`.
- **Resolução do jogo** (`MainActivity`, `Prefs.window`; Configurações › **Resolução**, ou a de um jogo próprio em Configurações do jogo): o tamanho de janela que o host dá ao jogo, a partir do próximo início: **Celular 1080p** (o padrão, `DM_WINDOW_SIZE=1920x1080`; o `android_window` de um profile pode dar ao jogo outro padrão quando o usuário não escolheu nenhum, nesta tela ou nas configurações próprias do jogo: nenhum profile define um agora; o Celular 720p do Donkey Kong Bananza da v0.1.2 foi junto com a correção do upscaler e o piso de clock de GPU do Turnip), **Original** (`DM_WINDOW_SIZE=original`, o tamanho próprio do jogo: 2880x1620 em Donkey Kong Bananza) ou **Celular 720p** (`DM_WINDOW_SIZE=1280x720`: menos tempo de GPU por frame num celular limitado pela GPU; economiza só dezenas de MB de memória, a memória própria do jogo não depende dela). A configuração guarda o próprio tamanho, e novos tamanhos são acrescentados ao fim da lista. O host o escreve nas funções de tamanho de janela do jogo no carregamento (chave do profile `window_fn`, `loader.c` `window_apply`; a linha do log `window: …`); os render targets escalam com a janela. Um jogo sem linha `window_fn` para a build dele mantém o tamanho próprio. Um jogo que dimensiona as cenas pela escala gráfica do Switch 2 em vez da janela tem linhas `graphics_scale` no profile ([a chave](../dm/games/README.md#chaves)): a mesma escolha então define `DM_GRAPHICS_SCALE` e `DM_OPMODE` pela linha da escolha e nenhum `DM_WINDOW_SIZE` (Mario Kart World: 1080p = escala de handheld 0, 1920x1080; 720p = escala de handheld 2, 1280x720; Original = o próprio dele, escala de console 1, 2048x1152; [Render resolution](../dm/games/0400C3F00006E000/README.md#resolucao-de-renderizacao-android-180)). De qual alavanca um jogo dispõe vem do profile (`Profile.resolutionEnv`, `resolutionOf` no build.gradle); um jogo sem nenhuma não recebe a linha de resolução do jogo nas Configurações do jogo, e Configurações mostra o padrão só quando um jogo do APK tem um. As linhas do `env.txt` ainda vencem para uma execução. `DM_WINDOW_SIZE=<w>x<h>` no `env.txt` sobrepõe a configuração para uma execução. O pack carrega as constantes próprias do jogo: um pack do Donkey Kong Bananza feito antes desta configuração as tem cortadas para 1920x1080, o que o host sobrescreve de qualquer jeito; para substituí-lo, rode o empacotador de novo (acima) e copie os novos arquivos `main.*` sobre a pasta de pack do celular ([a nota do jogo, Window size](../dm/games/040074A01BF12000/README.md#tamanho-da-janela)).
- **Painel dentro do jogo** (`SidePanel`, sobre o jogo em execução, que continua atrás dele): aberto pela aba ‹ pequena na borda direita (um quarto do caminho para baixo, sobre o HUD em vez dos controles), pelo Voltar do celular (botão ou gesto na borda), segurando o botão do topo ao centro dos controles na tela, ou pelo botão Home / guide de um gamepad (`KEYCODE_BUTTON_MODE`); fechado do mesmo jeito, por um toque ao lado dele ou pelo B. Com um gamepad, o D-pad se move por ele e A pressiona; nenhum input do pad chega ao jogo enquanto ele está aberto. Ele contém o limite de taxa de quadros, a geração de frames, o upscaling FSR 1, os itens do overlay, os controles na tela (opacidade, tamanho, vibração, o log, a posição da imagem e o editor de layout) e **Parar o jogo**. Cada mudança se aplica na hora e fica guardada para o próximo início.
- **Pausa** (painel dentro do jogo, **Pausar o jogo**, e ao voltar): o jogo fica suspenso enquanto a tela aparece, com "Pausado, toque para continuar" sobre ela; um toque, ou A / Start num gamepad, continua. Com **Pausar ao voltar** ligado (por jogo, ligado por padrão: nas Configurações do jogo, ou a caixa do painel dentro do jogo), a tela que volta do segundo plano aparece pausada em vez de deixá-la rodar na hora. Suspenso (pausado, ou no segundo plano) significa: relógio do guest congelado, gráficos drenados e barrados, toda thread do guest parada no próximo SVC, gate de spin ou sleep (`dm_guest_suspend`, `hle_os.c`: o Horizon suspende o processo inteiro, e os sleeps e esperas cronometradas do guest rodam no tempo do host, então um relógio congelado sozinho as deixava acordando), áudio suspenso (o sumidouro silencioso ocioso), os sensores de movimento desligados, o overlay do launcher e a cauda do log ociosos, o watchdog não contando nenhuma paralisação (um jogo que não confirmou o save dele mantém esse progresso só na memória nesse meio-tempo, congelado como o suspend do Horizon o congela: parar o jogo enquanto pausado ou no segundo plano o perde); o jogo é avisado Background (foco 3 depois de 2), e OutOfFocus e depois InFocus quando continua (eventos 4 / 5 do `nxhost_lifecycle`). Cada mudança registra `[lifecycle] paused | continued | background | foreground: threads' CPU since the last pause or resume <s> in <s> (<n> threads); busiest: …` de `/proc/self/task`, então um segundo plano ou uma pausa mostra o que ainda rodou.
- **Limite de taxa de quadros** (painel dentro do jogo, `DM_FPS_TARGET`; guardado como o limite do próprio jogo em execução, `fps_cap@<title ID>`; o das Configurações é o padrão dos demais): o próprio do jogo, 60, 30, 20 ou 15 fps, definido enquanto o jogo roda (`nxhost_fps_cap_set`, `hle_fpslock.c` `dm_fps_target_set`). O host o escreve no limitador de taxa de quadros do próprio jogo, então o jogo roda naquela taxa e na velocidade certa; uma taxa que o limitador do jogo não consegue segurar fica acinzentada. 40 e 45 não são oferecidos: um jogo que avança a lógica pelo intervalo de present roda em velocidade errada nelas ([O piso de um controlador de intervalo dinâmico, e limites definidos enquanto o jogo roda](../docs/reference/frame-rate.md#a-dynamic-interval-controllers-floor-and-caps-set-while-the-game-runs)); um 40 ou 45 guardado lê como 30 (`Prefs.capOf`). Um jogo que escolhe a própria taxa de quadros (o status do limite do host não informa taxa que ele possa segurar) não recebe opções de limite: o painel dentro do jogo mostra uma linha em vez disso, e quando uma execução já a viu (`own_rate@<title ID>`, escrito 30 s depois do início e pelo painel) as Configurações do jogo mostram o limite como "Este jogo escolhe a própria taxa de quadros". O limite é a taxa própria do jogo; a geração de frames (abaixo) é uma configuração separada que acrescenta frames gerados por cima.
- **As configurações são mantidas** entre reinícios de jogo e de app: o launcher (processo principal) e o jogo (`:game`) compartilham os arquivos de preferências, lidos de novo sempre que o outro processo os escreveu (`Prefs.open`, `MODE_MULTI_PROCESS`), e cada mudança é escrita na hora (`commit`), então parar o jogo, que termina o processo dele, não perde nada.
- **Geração de frames (LSFG)**, desligada por padrão: a geração de frames do Lossless Scaling, com o `Lossless.dll` do próprio usuário (Lossless Scaling para Windows). O launcher procura por ele, nesta ordem, em `Documents/Emulation/bios/Lossless.dll`, `Switch2/Lossless.dll`, `Download/Lossless.dll` e `Android/data/<app>/files/Lossless.dll` no armazenamento do celular, e copia o primeiro que encontrar para os arquivos privados do app (de novo quando ele muda); Configurações › **Geração de frames** mostra o que ele encontrou e tem **Escolher Lossless.dll** para um arquivo em outro lugar. As configurações (Configurações › Geração de frames, ou no jogo: o painel dentro do jogo): ligada / desligada, frames por frame do jogo (2x, 3x, 4x), uma taxa de quadros alvo em vez disso (60, 90, 120: o multiplicador a segue, o pacer do Eden), e a resolução da estimativa de movimento (Auto = a resolução própria do jogo, 25–100 %). Mudanças no jogo valem a partir do próximo frame. O host as recebe como `DM_LSFG=0/1`, `DM_LSFG_MULT`, `DM_LSFG_TARGET`, `DM_LSFG_FLOW` (0 = auto) e `DM_LSFG_DLL` (a cópia), que o `env.txt` pode sobrepor. Os frames gerados são apresentados entre os frames do jogo, cada um segurado pela sua parte do intervalo de frame medido do jogo (ritmo de exibição); o frame próprio do jogo é mostrado por último, então a imagem fica um frame do jogo atrás. Precisa de `shaderFloat16`, storage images de R8 / RGBA8 / RGBA16F e descritores nulos; sem eles, ou sem uma DLL utilizável, o overlay diz `LSFG unavailable` e o log traz `[RED] vk: frame generation unavailable: <why>`. Só o conjunto de shaders de desempenho do Eden é usado.
- **Upscaling FSR 1** (painel dentro do jogo, **Upscaling**, `Fsr`, desligado por padrão; guardado para os próximos inícios, `fsr` / `fsr_sharp`): AMD FidelityFX Super Resolution 1 no lugar do escalonamento bilinear quando a imagem é menor que a tela (`DM_VK_FSR`, `DM_VK_FSR_SHARP`: `dm/gfx/vk_android/vka_present.c`), com a nitidez Max, Default, Soft ou Softer (0, 0.25, 0.5, 1 passos). Uma mudança chega ao jogo em execução como linhas `env` do arquivo de controle vivo dele (`DM_CTL`, [TESTING.md](TESTING.md#live-control)) e se aplica no próximo frame; uma linha `DM_VK_FSR=…` no `env.txt` ou `env-<title ID>.txt` vence no início.

## Verificação de prontidão

O que um celular precisa ter para um jogo, conferido antes do jogo começar e numa tela própria (Configurações › **Verificação de prontidão**), para que uma pessoa num celular que não tem algo receba uma frase nomeando o que falta em vez de uma quebra ou uma imagem quebrada.

**Testado:** um celular, um Honor PNM-N49 (Adreno 840, 16 GB, Android 17) com o driver Qualcomm próprio (driver ID 8, `QUALCOMM_PROPRIETARY`), e as builds Turnip de [Drivers de GPU personalizados](#drivers-de-gpu-personalizados). Todo outro celular, GPU e driver está não testado: os requisitos abaixo são o que o código e as bibliotecas de shaders precisam, não uma lista de celulares que funcionam.

| Classe | O quê | O que a ausência significa |
|---|---|---|
| Todo jogo: o celular | ARM de 64 bits, Android 13 (SDK 33) ou mais novo, Acesso a todos os arquivos | o app não instala, ou não consegue ler o jogo |
| Todo jogo: Vulkan | Vulkan 1.3 (loader e driver), uma fila de gráficos + compute, timeline semaphores, dynamic rendering (`vka_dev.c` para sem eles); `VK_KHR_swapchain`, `VK_KHR_map_memory2` + `VK_EXT_map_memory_placed` (`memoryMapPlaced`), arrays de imagens sampled update-after-bind (parcialmente ligados, runtime arrays) | o host para, ou roda e não desenha nem mostra nada |
| Por jogo: memória | pelo menos o `ram_gib` do jogo (ActivityManager `totalMem`, que num celular de 16 GB é uns 14.5-15.5 GiB) | obrigatório: o Android para o jogo; degradado: testado em mais celulares apenas |
| Por jogo: recursos de shader | os recursos que a biblioteca de shaders do jogo usa (geometry shaders, storage images sem formato, draw parameters, buffer device addresses, inteiros de 64 bits ...), e `maxComputeSharedMemorySize` pelo menos o do maior compute shader dele | obrigatório: aqueles draws são pulados ou os pipelines falham; degradado: alguns shaders |
| Por jogo: texturas | `textureCompressionBC` e `textureCompressionASTC_LDR` (as texturas são amostradas nos formatos próprios, nunca decodificadas na CPU) | aquela textura fica ausente |
| Por jogo: texturas sparse | sparse residency images (binding, residency 2D, a forma padrão de blocos, leituras estritamente não residentes, na fila) e sparse residency por formato (BC6H, ASTC 8x8 ...) | degradado: um array de texturas vira uma imagem densa começando num nível mais grosseiro (menos detalhe, mais memória). Um formato com sparse residency ocupa só os tiles que o jogo mapeia (`vka_sparse.c`); um sem ela recebe uma imagem densa a partir do nível mais fino que caiba em `DM_VK_SPARSE_DENSE_MB` (`vka_tex.c` `dense_floor`) |

As linhas próprias de cada jogo estão no profile dele, `dm/games/<title ID>/readiness.tsv` ([o formato](../dm/games/README.md#linhas-de-prontidao)), com uma linha de status (`playable` ou `bring-up`: um jogo em bring-up recebe um aviso em todo celular). As necessidades próprias do host são `Readiness.HOST` (espelham `vka_dev.c`).

- **Os fatos** (`nxhost_vk_readiness`, `dm/gfx/vk_android/vka_readiness.c`): uma instância própria no driver que o jogo carregaria (a escolha do launcher ou uma linha `DM_VK_DRIVER`, aberta uma vez por processo, então o replay recebe a mesma biblioteca), o primeiro dispositivo físico (o que o replay pega), nenhum dispositivo: a versão da API, o nome da GPU, os IDs de vendor e de device, o nome, a info, o ID (`VkDriverId`) e a versão do driver, o nome de um driver personalizado, os recursos e limites acima, as extensões, a fila, as propriedades sparse, por formato se um array 2D de sparse residency pode ser criado (como `vka_tex.c` pede), e o heap local do dispositivo. Nada conhece um vendor: um driver personalizado é conferido pelo que ele informa. O launcher acrescenta `ram_gib` e `android.sdk`.
- **Antes de um início** (`GameActivity.readinessHold`, depois das conferências de pack e RomFS, antes de o save ser trancado e `nxhost_main` iniciar; no máximo 8 s: uma conferência que não responde, ou um host que não consegue informar, dá um aviso "not checked", nunca uma falha): itens obrigatórios ausentes → **Não está pronto para este jogo**: os itens ausentes nomeados, e **Voltar**, **Detalhes** ou **Tentar mesmo assim**; quando os mapas de memória posicionada estão ausentes (`VK_KHR_map_memory2`, `VK_EXT_map_memory_placed`, `memoryMapPlaced`) ele diz com clareza que com este driver nada é desenhado (tela preta), sugere Sistema (ou, no Sistema, um driver personalizado que os tenha), e o botão diz **Iniciar mesmo assim (tela preta)**; **Detalhes** traz cada item com o que o driver informa e o que o jogo precisa, a GPU e o driver, e **Copiar relatório**. Itens degradados (ou um jogo em bring-up) → **Pronto, com limites**: **Continuar** (um toque), uma caixa **Não mostrar isso de novo** (até a GPU, o driver ou os avisos mudarem), **Voltar** e **Detalhes**; Configurações › Verificação de prontidão mostra os detalhes de novo. O log recebe uma linha, `[readiness] <title ID>: PASS|WARN|FAIL; <GPU e driver>; RAM …; missing (required): …; missing (degraded): …` (e "a pessoa escolheu Tentar mesmo assim"), e `files/readiness-<title ID>.txt` o relatório completo daquela inicialização.
- **A tela** (`ReadinessActivity`, no processo próprio `:readiness`, que carrega o host do primeiro jogo para perguntar à GPU): um veredicto (Pronto, Pronto com limites, Não está pronto) com **Rodar de novo**, **Compartilhar** (um toque longo copia) e **Copiar relatório**, depois linhas de aprovação / aviso / falha para o celular (Android e ABI, memória, Acesso a todos os arquivos, armazenamento livre, restrições de bateria, a última saída de jogo e as mortes por memória dos últimos 7 dias dos registros de saída do Android, as chaves do `env.txt` do app de teste), a GPU e o driver, e cada jogo do APK (nomeado como o jogo adicionado pela pessoa, senão pelo title ID); os detalhes de uma linha abrem num toque (falhas e avisos, e os fatos da GPU, abertos desde o início, com um botão de correção quando há um: **Permitir acesso a arquivos**, **Abrir as configurações do app**, **Escolher um driver de GPU**). O relatório é a conferência inteira como texto, com a última conferência de inicialização de cada jogo e todos os fatos, para um relatório de compatibilidade. Um jogo com um driver próprio é conferido nesse driver quando inicia: a linha **Driver de GPU próprio** dele é um aviso quando esse driver difere do que a tela conferiu (o driver abre uma vez por processo, então a tela não consegue sondar um segundo).
- **O celular testado** (2026-11-03, com o driver próprio; os fatos estão em `android/app/src/jvmtest/honor-pnm-n49.readiness.txt`): Adreno (TM) 840, Vulkan 1.4.295, Qualcomm 718a07726a (driver ID 8, versão `0x8034a02c`), 14,7 GiB; toda necessidade do host presente. Dos dois jogos, um passa em toda conferência, o outro (em bring-up) avisa: `maxComputeSharedMemorySize` é 32.768 onde 168 dos compute shaders dele pedem 49.152, e nenhum formato comprimido em bloco tem sparse residency (RGBA8 e RGBA16F têm), então os arrays BC6H e ASTC 8x8 dele começam num nível mais grosseiro. Ele também informa `VK_EXT_mesh_shader` com `meshShader` e `taskShader` (memória compartilhada de mesh / task de 32.768), nenhum `shaderFloat64`, subgrupos de 64.
- **Testes:** `dm/tools/tests/test_android_readiness.py` (as decisões na JVM; as linhas de todo profile nomeiam um fato que o host ou o launcher informam).

## Drivers de GPU personalizados

O replay roda no driver Vulkan próprio do celular (**Sistema**) a menos que outro seja escolhido. Um driver personalizado é um zip no layout que o Eden e outros apps de Android usam: o `.so` do driver, o que quer que ele carregue, e um `meta.json` cujo `libraryName` nomeia o `.so`.

- **Instalar e escolher:** Configurações › **Driver de GPU** → **Instalar…** → **Escolher um zip…** (o seletor de arquivos do sistema), **Baixar…** (os lançamentos públicos do GitHub dos repositórios em `DriverFetch.REPOS`; só num toque), ou um zip posto no `Android/data/<app>/files/gpu_drivers/` do próprio app (listado pelo nome). O launcher nunca abre arquivos em outras pastas (Download, …) por conta própria. O zip é descompactado fora da UI thread nos arquivos privados do app, `files/gpu_drivers/<nome>/`, o único lugar de onde uma biblioteca pode ser carregada, e o escolhido vai para o host como `DM_VK_DRIVER=<essa pasta>` quando o jogo inicia. **Sistema** não passa nada. adb: `am start -n dev.ankanative.android.test/dev.nxnative.android.MainActivity --es gpu_driver_zip <zip path>` instala e escolhe um zip, `--es gpu_driver system` volta atrás.
- **Uma instalação falha** (`DriverZip`) é uma mensagem, nunca uma quebra: um zip danificado, um nome de entrada que não é UTF-8 (o leitor de zip do Java lança `IllegalArgumentException` para isso), nenhum `meta.json`, uma biblioteca ausente, mais de 256 arquivos ou 512 MB descompactados. Ele é descompactado primeiro em `gpu_drivers/.installing` e substitui um driver instalado de mesmo nome só depois de conferido, então uma falha deixa os drivers instalados e a escolha como estavam. Testes: `python3 dm/tools/tests/test_android_driverzip.py`.
- **Host:** `DM_VK_DRIVER=<pasta>` (ou um `.so`) carrega aquele driver através do libadrenotools (`vka_driver.c`; `dm/third_party/libadrenotools`); uma linha `DM_VK_DRIVER` no `env.txt` vence a escolha do launcher. `DM_VK_HOOKDIR` sobrepõe onde ficam as bibliotecas de hook (por padrão ao lado de `libnxhost.so` no APK). Ambas exigem reinício. A linha `[vk] driver: <name> (<info>), driver ID <n>` do log diz qual rodou; cada driver mantém o seu próprio arquivo de cache de pipelines.
- **Padrões por driver** se ancoram no `VkPhysicalDeviceDriverProperties.driverID` (`V.driver_id`) e em consultas de recursos, nunca no nome do driver, e cada um mantém a sua chave:
  - Tamanhos de subgrupo (todos os drivers, pelo que o dispositivo informa; [Shaders de subgrupo nos subgrupos de 128 lanes do Turnip](../docs/reference/shaders.md#subgroup-shaders-at-turnips-128-lane-subgroups)): os shaders de subgrupo de fragment e compute do Turnip ficam fixos nas 64 lanes da biblioteca, os estágios de vertex e tesselação também onde ele permite, e o estágio de geometry roda subgrupos de uma lane (`VK_DRIVER_ID_MESA_TURNIP`; `DM_VK_SUBGROUP_GS=1` desfaz isso). `DM_VK_SUBGROUP_PIN` 0 / 1 / máscara de estágio. O driver da Qualcomm: inalterado.
  - Baralhos de subgrupo de compute ([HMMA da Ampere e baralhos de warp do upscaler da agl na Adreno](../docs/reference/shaders.md#ampere-hmma-and-warp-shuffles-of-agls-upscaler-on-adreno)): no Turnip, os pipelines de compute pegam o módulo da biblioteca com os baralhos através da memória de workgroup (o ir3 transforma cada baralho de índice num laço); `DM_VK_SHUFFLE_LDS` 0 / 1 (reinício). O driver da Qualcomm: a instrução de shuffle.
  - O piso de clock da GPU (`DM_VK_GPU_FLOOR`): através de `VK_QCOM_queue_perf_hint` no driver da Qualcomm; em todo outro driver (Turnip) através da sessão ADPF, que informa o vão e o tempo de GPU de cada frame contra o período mais curto do jogo (`DM_VK_GPU_FLOOR_ADPF`, desde 2026-11-05; [Um piso de clock de GPU que segue o período do present segura um intervalo dinâmico no ponto mais lento dele](../docs/reference/frame-rate.md#a-gpu-clock-floor-that-follows-the-present-period-holds-a-dynamic-interval-at-its-slowest)).
  - O pré-fault dos mapas posicionados (`vka_mem.c`), a reivindicação de geometry shader (`DM_VK_GS_CLAIM`), as listas de formatos UBWC (`DM_VK_UBWC`) e as divisões de pass (`DM_VK_CHUNK_PASS`) continuam ligados em todo driver: ainda não medidos no Turnip (em aberto). `DM_VK_PREFAULT=0` pula o pré-fault, um diagnóstico para essa medição (com o teste de memória posicionada do `DM_VK_NANSCAN=1`).
- **Resultados** no Honor PNM-N49 (Adreno 840), primeiro nível do DKB, execuções em fastboot, tetos de CPU 3,63 / 4,61 GHz (2026-11-02, build 3ee6e248):

  | Driver | driverID | Subiu | Imagem | fps | Frame p50 / p95 ms | Gravação ms | GPU ms |
  |---|---|---|---|---|---|---|---|
  | Sistema (Qualcomm 718a07726a) | 8 (QUALCOMM_PROPRIETARY) | sim | correta | 44 (overlay 31) | 25.5 / 36.1 | 19.4 | 20.9 |
  | Turnip Mainline v32 (whitebelyash, Mesa 26.3.0-devel) | 18 (MESA_TURNIP) | sim | correta (paredes pretas antes da correção de subgrupo) | 22 | 48.9 / 53.7 | 31.1 | 37.8 |

  Todo Turnip que subiu tem todo recurso que o replay precisa (mapas posicionados, push descriptors, vertex input dynamic state, descritores nulos, update-after-bind, timeline semaphores) e só não tem `VK_QCOM_queue_perf_hint`; o piso de clock de GPU do replay passa pelo driver do kernel em vez disso (a restrição de energia do contexto de fila do Turnip, [a entrada](../docs/reference/frame-rate.md#a-gpu-clock-floor-that-follows-the-present-period-holds-a-dynamic-interval-at-its-slowest)). Um driver sem mapas posicionados deixaria a GPU sem os pools de memória do jogo (`[RED] vk: no VK_EXT_map_memory_placed`); o caminho de draw tem soluções de contorno para os outros. O Sistema é o mais rápido: no Turnip a gravação leva 4,2-4,4 µs por draw em vez de 2,4 (em aberto: onde), então o controle do jogo fica preso a 20 fps; entre os Turnip, o tempo de GPU do T30 fica um terço abaixo do do v32. O seletor não marca nenhum driver como recomendado (`GpuDriver.RECOMMENDED_NAME_PREFIX` vazio).

### A interface do launcher com o host

O shim JNI do launcher (`android/app/src/main/cpp/nxlaunch.c`) inclui os cabeçalhos próprios do host, [`dm/host/android/input_android.h`](../dm/host/android/input_android.h) e [`dm/gfx/vk_android/vk_android.h`](../dm/gfx/vk_android/vk_android.h), e declara cada ponto de entrada como weak: as assinaturas não podem divergir, e um host sem um deles ainda carrega (a chamada não faz nada; o log diz `[nxlaunch] hooks: window …, input …, lifecycle …`). `GameActivity` e `SelftestActivity` os chamam através de `Native`. O jogo roda no processo `:game`, então as chamadas de janela, input e lifecycle dele chegam ao `libnxhost.so` desse processo. O `JNI_OnLoad` do `libnxhost.so` procura a classe Kotlin opcional `dev.nxnative.NxHost` ([PORTING.md](PORTING.md#launcher-interface)); este launcher não tem nenhuma, então não vincula nada e retorna normalmente.

| Função | Quando é chamada |
|---|---|
| `nxhost_set_window(ANativeWindow *)` | de `surfaceCreated` / `surfaceChanged`, e com `NULL` de `surfaceDestroyed`; o launcher libera a referência própria depois da chamada, o replay mantém uma |
| `nxhost_vk_selftest(ANativeWindow *, int frames)` | pelo `SelftestActivity`, com 600 frames, numa thread própria |
| `nxhost_vk_readiness(buf, n)` | pelo `GameActivity` antes de o host iniciar (com o driver do jogo em `DM_VK_DRIVER`) e pelo `ReadinessActivity`, numa thread própria: os fatos de Vulkan da [verificação de prontidão](#verificacao-de-prontidao) |
| `nxhost_input_device_added` / `_removed` | de um `InputDeviceListener`, para os gamepads presentes no início e os que entram e saem |
| `nxhost_input_key(device, keycode, down)` | cada evento de tecla de um gamepad ou D-pad de um dispositivo real; o evento é consumido quando ela devolve true (um botão de pad). Voltar, Home (`BUTTON_MODE`: o painel dentro do jogo) e teclados ficam com o launcher; enquanto o painel está aberto, nenhuma tecla nem eixo do pad chega ao host |
| `nxhost_input_axes(device, axes, values, n)` | cada `ACTION_MOVE` de joystick, com só os eixos que o dispositivo tem (`getMotionRange`) de X, Y, Z, RZ, RX, RY, HAT_X, HAT_Y, LTRIGGER, RTRIGGER, GAS, BRAKE |
| `nxhost_input_touch(action, pointer, x, y)`, `nxhost_touch_layout` | cada toque na tela (de `TouchControls`, a view sobre a superfície), normalizados para a view; o layout dá o retângulo da imagem 16:9 em que o replay faz letterbox |
| `nxhost_picture_place(x, y)` | onde a imagem em letterbox fica no espaço livre da janela (0 esquerda / topo, 0,5 centralizada, 1 direita / base), nunca escalada; de `TouchControls` com cada layout e do editor |
| `nxhost_touch_controls_set`, `_state`, `_enable` | `TouchControls` posiciona os controles na tela (em unidades de 1/135 de polegada) e entrega o layout ao host, que decide para cada toque se ele aciona um controle ou é um dedo na tela sensível; a view lê de volta o que cada controle contém (para desenhá-lo e dar o toque) e os desliga enquanto um gamepad está conectado ou o usuário os esconde |
| `nxhost_lifecycle(0 … 3)`, `nxhost_motion_start` / `_stop` / `_rotation` | `onPause` 0 (e os movimento param), `onStop` 1, `onStart` 2, `onResume` 3 (e os movimento começam); a rotação no início e em cada mudança de configuração |
| `nxhost_audio_interrupt`, `nxhost_audio_route_changed` | do ouvinte de foco de áudio (`USAGE_GAME`) e de um `AudioDeviceCallback` |
| `nxhost_fps(out, n)` | duas vezes por segundo pelo `GameActivity` para o overlay: fps do jogo, fps apresentado, tempo de frame, estado da geração de frames, imagens por frame do jogo, ms de GPU por frame |
| `nxhost_framegen_set(on, multiplier, target, flow)`, `nxhost_framegen_status(buf, n)` | do painel dentro do jogo; o estado e o motivo dele, mostrados nele |
| `nxhost_fps_cap_set(fps)`, `nxhost_fps_cap_status(buf, n)` | do painel dentro do jogo: o limite de taxa de quadros, e "`<cap> <rates> <game fps>`" duas vezes por segundo enquanto o painel está aberto (quais limites este jogo consegue segurar, em qual taxa ele roda) |
