# Hand-over: shader delta update and play while updating (2026-11-04, branch `android-delta`)

Branch `android-delta` (worktree `nxnative-android-delta`), from android-int `adf419ad`. Not pushed, not merged. Library version `6607c8d19abc`, ABI `01b52a48538b`.

## What is done

- **Delta update (tools).** `dm/gfx/tools/vk_android_delta.py`: the entry hash (one shader's library entry without its file positions, codec or header versions), the manifest `dm/games/<id>/vk_delta.tsv` (keys and hashes only, `manifest_problems` refuses any other line form), the ABI digest. `vk_android_build.py`: with a manifest of its version, entries of older libraries (`DMSH_VK_DELTA_FROM`, else the cache folder's other `v-<V>`) whose hash matches become result files, only the rest is translated; progress counts the shaders translated; the new library is hashed, `vk_delta.tsv` written beside it, every entry checked against the manifest (`[RED] delta check:` / `[RED] delta:` lines name key and reason). `--publish-delta <v-V dir> [older libs…]` puts a full build's manifest into the profile with `from` rows. DKB's manifest for `6607c8d19abc` is committed (777 KB).
- **Play while updating.** The library header's reserved 12 bytes carry `abi` (`DMSH_VK_ABI`, `dmsh_chain_vk.h`; `DMSH_VK_ABI_REV` in `dmsh_abi_vk.h` for conventions neither header shows). `vka_shlib_check` takes an ABI; `vka_shader.c lib_load` plays the newest other `v-<V>` of the pack with the host's ABI while its own version is missing; captures record the library loaded.
- **App.** `ShaderLibs.java` (pure Java): header, playable older library, shaders to translate from the profile's `from` rows (`Profile.delta`, a new `NX_PROFILES` column), time estimate. The game card starts the shaders job by itself when the pack has an older library the manifest knows (`Ondevice.autoUpdate`, once per process); Play stays on ("Ready · updating shaders") when that library has this ABI; Prepare's dialogs give the delta's count and time. `PackService` passes `DMSH_VK_DELTA_FROM=<pack>/shaders`; the job shows the tool's total and a "Checking the shader library" stage.
- **Docs:** `android/SHADERS.md` (Delta updates, the simulation, header `abi`, replay step 1), `android/ONDEVICE.md` (pack check, Progress, shaders step environment, Shader updates).

## Open

1. **Not run on the phone.** No phone test was done (none was asked for). To check: an APK of this branch over a pack with `v-66d1dd2cd5ff` → the card starts the job alone, `shaders.log` shows `delta: 22852 of 22852 shaders kept`, the step's own time, then the pack has `v-6607c8d19abc` byte-identical to the Mac's (SHA-256 `60022b17d925c8f0…`).
2. **Libraries without an ABI (66d1dd2cd5ff and older) never block Play** (the user's decision, 2026-11-04): the replay plays the newest one as a last resort with a `[RED]` warning, and the launcher shows "Ready · shaders need one update", a chip and a toast suggesting one more shader update (after which updates are deltas of the same ABI). For DKB's release library the modules are those of 6607c8d19abc, so it draws right; a much older one (b430e271aa8a) could draw wrong until updated. Not run on the phone; `lib_load` is Android-only code, checked by compiling only.
3. **The split still runs on every update** (the finished job deletes `split/`): 4-8 min of an update that translates nothing. Keeping the 218 MB package, or skipping the split when the delta translates 0 shaders, would make such an update about a minute.
4. **Publishing is a release step.** Each tools change that ships needs a full Mac build and `--publish-delta` (with the previous release's library as an argument for its `from` row); without it phones make a full build. `test_android_shader_delta` only warns about a stale manifest.
5. **Merge with the Retry fix** (uncommitted in android-int): both touch `PackService.java` (different hunks) and `ONDEVICE.md` (this branch leaves the switches line alone; the Shader updates bullet is new). `ShaderResults` drops only failed results; kept results are `ok`.
6. Old libraries stay in the pack (about 365 MB each) as before; nothing deletes them after an update.
7. The auto-start resumes a failed or paused job once per app process; a job that fails every time is retried on each app start.
