# Perfis de jogo

Cada jogo que o port conhece tem uma pasta `dm/games/<id>/`, nomeada pelo title ID do jogo base: o de Ocarina of Time é `0400486024DEC000`, o de Donkey Kong Bananza é `040074A01BF12000`. A pasta contém:

- **`game.tsv`**: as constantes do jogo, uma linha `chave<TAB>valor` cada, com comentários em linhas próprias.
- **As tabelas de shader** que `shader_split.py` escreve: `shader_map.tsv` (+ `.conflicts.tsv`), `shader_facts.tsv`, `shader_pairs.tsv` e `pso_pairs.tsv` (variações de programa agl BAHS suplementares e coberturas de entrada de pass do Unity legadas). As duas tabelas de pares alimentam o padding de saída de vertex e o prebuild do pipeline; para um perfil sem `pso_pairs.tsv`, o script do NSP mantém a tabela gerada ao lado do pacote de shaders.
- **`shader_facts_manual.tsv`** (opcional): fatos de tradução escritos à mão no formato de linha do `shader_facts.tsv`, para o que o código de máquina não diz (Link's Awakening: uma entrada de vértice em que o palpite de entrada inteira acerta errado; Breath of the Wild e Tears of the Kingdom: saídas de fragment inteiras, que um jogo sem versão para PC não tem outra fonte para obter). O `shader_split.py` a mescla sobre as linhas geradas; como a tabela está na cadeia, mudá-la muda só a versão da cadeia daquele perfil.
- **`pso_manifest.tsv`**: a lista de semente de prewarm.
- **`shader_seen.tsv`** (opcional): chaves de shader que as execuções Mac de um jogo pediram, para uma biblioteca parcial que contém só aquelas ([Compilando shaders selecionados do Mac](../../docs/development.md#building-selected-mac-shaders)). Nenhuma ferramenta a lê sozinha, e ela não é uma entrada de shader.
- **`bench.tsv`** (opcional): rotas de benchmark para `scripts/bench.py` ([Um benchmark no Mac](../../docs/development.md#a-benchmark-on-the-mac)): um nome, a entrada roteirizada (`DM_KEYS`), a janela medida e uma descrição, uma rota por linha.
- **`vk_capture.tsv`** (um jogo Vulkan que gera seus shaders em tempo de execução, Super Mario Galaxy): as chaves dos módulos SPIR-V que ele gera.
- **`gl_capture.tsv`** (um jogo OpenGL que monta seu GLSL em tempo de execução, Balatro): os arquivos (`<key>.vert` / `<key>.frag`) dos shaders que ele compila.
- **`bf_want.tsv`**.
- **`dual_want.tsv`** (opcional): pixel shaders que um pipeline mistura com sua saída 1 como segunda fonte (dual-source blending); o `dmsh_build.py` dá a cada um um entry point de fonte dupla (`fs_dual`). O host os lista com `DM_NVN_DUAL_WANT=<arquivo>` ([Uma fonte de mistura secundária escrita](../../docs/reference/rendering.md#a-written-secondary-blend-source-nvn-dual-source-blending)).
- **`validated.tsv`** (opcional): a cadeia em que este jogo esteve verde pela última vez, escrita por `scripts/regress.py check --record` (ou `baseline --record`) quando seu status de comparação é `PASS` ou `CHANGED` e toda execução de boot testada tem sucesso. Uma falha de boot compartilhada com a baseline ainda impede a gravação. Linhas `quick` / `full` (a mais recente de cada), `modo<TAB>chain=<DMSH_CHAIN> commit=<SHA curto>[+dirty] date=<dia UTC> machine=<modelo> macos=<versão>`; um resultado vermelho deixa as linhas como estavam. Um build que usa um perfil derivado não valida o perfil do repositório. O `regress.py list` a mostra e diz se aquela cadeia é a atual. Ela não contém dados do jogo; commite-a com o pull request.
- **`geo_mesh.tsv`** (opcional): pares de vertex / geometry shader desenhados com um geometry shader passthrough; o `dmsh_build.py` constrói uma biblioteca de mesh para cada um (`dmsh_mesh.py`), e o host desenha as triangle lists de tal par como mesh draws ([Geometry shaders passthrough desenhados pelo vertex shader](../../docs/reference/shaders.md#passthrough-geometry-shaders-drawn-by-the-vertex-shader)). Um par não listado pega o caminho de compute.
- **`README.md`**: as notas do jogo: o que seu perfil precisa e por quê, o que foi encontrado nele, como chegar a uma cena no Mac, o que ainda está em aberto. Listado em [Jogos](#jogos).
- **`patches.py`** (opcional): os patches do rewriter das próprias builds do jogo (`main`), indexados pelo NSO build ID: `CUTS` (cortes de bytes, cada original asserido), `OBS` (portões de observação) e `FRAME_STEP` (stubs de frame-step). O `dm/tools/patch_nso.py` carrega o arquivo de todo perfil e aplica os de uma build de módulo, de onde quer que ela venha; uma build reivindicada duas vezes para a reescrita. Um perfil provisório (em `DM_GAMES_DIR`) também pode ter um, que o rewriter e o passo de reescrita do script do NSP aceitam igualmente. Cortes dos módulos `sdk` da Nintendo, que vários jogos trazem, estão em `dm/tools/sdk_patches.py`. O `MATCH_CUTS` opcional pode localizar cortes verificados em builds não registradas do jogo selecionado por fingerprints de função (um patch de várias funções se aplica inteira ou nada); veja [Cortes casados por função para builds não registradas](../../docs/reference/rewriter.md#function-matched-cuts-for-unregistered-builds) para inscrição, precedência de perfis e limites. Um jogo sem patches não tem arquivo, e um perfil derivado usa as regras do seu perfil no repositório. O `dm/tools/tests/test_patches.py` verifica que um arquivo nomeia só as builds do seu próprio perfil. `BINDING` (não lido pelo rewriter, obrigatório pelo `test_patches.py`) declara o binding de cada patch agora, o mais frouxo que poderia ter, sua finalidade e por quê ([Binding](../../docs/agents/game-patches.md#binding)); um bring-up que ainda não pode julgar a meta de um patch preso a uma build diz `'goal': 'unreviewed'` em vez de chutar; depois de mudar um arquivo de patches, uma tabela do host indexada por build ou uma chave de perfil, rode `dm/tools/docs_patches.py` para atualizar o [índice de patches](../../docs/agents/game-patches.md).

A versão da cadeia não está no perfil: uma versão serve a todo jogo (`dm/gfx/nvn/dmsh_chain.h`, escrita por `dmsh_chain.py --header`). Duas tabelas a mais ficam na pasta do perfil mas não são commiteadas (o git as ignora). Uma execução completa do `dmsh_build.py` faz as duas a partir das suas saídas Mac, então cada checkout faz as suas, e carimba suas bibliotecas com o digest das entradas do perfil (`b-<V>/inputs.tsv`, `dmsh_chain.py --inputs`). O host só aceita uma tabela quando seu cabeçalho nomeia a versão da cadeia da biblioteca dela e esse digest.
- **`c1_full.tsv`**: escrito pelo `c1_guard.py`. Sem ele, o c1 de cada shader ganha seus próprios 64 KiB.
- **`cb_extent.tsv`**: até onde em cada slot uniform cada shader pode ler, escrito pelo `cb_extent.py`. Sem ele, um uniform block que o jogo atualiza em parte dentro de um render pass é copiado inteiro.

Tudo que é específico de jogo pertence aqui. O código lê o perfil; ele não fixa um jogo no código.

| Quem | Escolhe o perfil com | Lê |
|---|---|---|
| Ferramentas de shader (`shader_split.py`, `dmsh_chain.py`, `dmsh_build.py`, `dmsh_facts.py`) | `DM_GAME=<id>` | tabelas, chaves `shader_*` |
| Host (`make -C dm/host`, `dm/gfx/tests`) | `GAME=<id>` | `gen/<id>/game_profile.h`, gerado de `game.tsv` por `game.py header` |
| `dm/ios/tools/build_ipa.sh` | `GAME=<id>` | nome do app, bundle ID, nome do IPA, módulos, marcador de RomFS, tabelas |
| `scripts/build_ipa_from_nsp.py` | o title ID dos NSPs | tudo acima. Sem perfil correspondente, escreve um survey, depois um perfil provisório fora do repositório e um IPA de melhor esforço (`--survey-only` para depois do survey) |

Nenhum deles tem um jogo padrão: sem um, eles param e listam os perfis. Para consultar um perfil:
- `python3 dm/games/game.py list` lista os perfis.
- `python3 dm/games/game.py <id> <chave>` imprime uma chave.

**Configurações do launcher.** O `settings.tsv` lista de uma vez as configurações voltadas ao usuário (a variável de ambiente que cada uma define, seu tipo, o valor padrão, a condição sob a qual um jogo a oferece e sua seção na tela única de configurações, **Game**, **Controls** ou **Performance**; Reset to tested defaults devolve a tela aos padrões do perfil, e Play então esquece as escolhas do launcher; seu cabeçalho descreve as colunas). Uma chave de perfil em que uma configuração tem valor padrão (`DM_GAME_<NAME>`) é o valor com que o jogo foi testado, que a página do usuário [docs/settings.md](../../docs/settings.md#tested-defaults) explica. O `build_ipa.sh` roda `settings.py <id> <módulos reescritos> <control.nacp> <out.json>`, que mantém as linhas que valem para o jogo: uma macro de perfil (`DM_GAME_FPS_TARGET!=0`), uma chave na tabela do rewriter de `main` (`RENDER_SCALE`, escrito pelo `patch_nso.py` para as builds com um stub de render scale), os idiomas do jogo. Ele os escreve no app como `dm/launcher.json`, de onde o launcher iOS (`dm/ios/Sources/Launcher.swift`) desenha sua tela; o script do NSP empacota a cópia do app Mac (`SETTINGS_PLATFORM=mac`, sem as linhas marcadas `platform:ios`, `Contents/Resources/dm/launcher.json`) para a janela de configurações do app Mac (`dm/mac/Launcher.swift`) e para as interfaces Mac. A última coluna opcional de uma linha, `meta`, traz campos `chave=valor` que as interfaces leem (`level=basic`, `needs=<VAR>=<valor>`; [Interfaces](../../docs/frontends.md#the-settings-list), com o JSON Schema em `docs/launcher.schema.json`), e o `render_base` de um perfil vai na linha do render scale como `base`, para que uma interface possa mostrar aquela configuração em pixels. Uma nova configuração para o usuário é uma linha; chaves de diagnóstico ficam só no ambiente.

Os padrões podem usar `<ios>|<mac>` para selecionar o valor da plataforma antes de resolver uma macro de perfil ou uma variável de build. Por exemplo, `DM_GAME_PSO_MTL4|1` segue o perfil no iOS e o padrão sempre-ligado do host Mac no Mac; `1|0` corresponde aos padrões iOS-ligado, Mac-desligado da thread de encode. O `SETTINGS_PLATFORM` aceita `ios` (o padrão) ou `mac`; outros valores são recusados.

## Chaves

| Chave | Significado |
|---|---|
| `title_id`, `program_id` | Identidade. O `program_id` é o que o `svcGetInfo(ProgramId)` reporta. O nome do jogo não fica armazenado: o script do NSP o lê dos dados de controle do NSP (NACP) |
| `name` | O nome do jogo, só um rótulo para o `game.py list`, mensagens de erro e o título da janela do Mac. O nome do app iOS é o nome do jogo nos dados de controle do NSP base e seu bundle ID é `org.nxnative.<title ID em minúsculas>`; o `APP_NAME` / `BUNDLE_ID` do script do NSP e o `DM_DISPLAY_NAME` / `DM_BUNDLE_ID` do `build_ipa.sh` os sobrescrevem |
| `ipa`, `app_category` | App iOS: o nome de arquivo IPA padrão e a categoria da App Store |
| `build <ver> <display version> <módulo>=<build ID>…` | Uma linha por versão em que o jogo foi trazido. O script do NSP monta qualquer versão (só o jogo base, qualquer update): uma registrada a partir do perfil como está, qualquer outra a partir de um perfil derivado dele (`<id>_build/profile`: as mesmas chaves, as tabelas de shader próprias daquela versão; `derive_profile`), com uma linha vermelha nomeando os módulos cuja build nenhuma linha registra, a qual os cortes por build e as correções do host não alcançam. O host reporta a display version pelo build ID de `main` |
| `package` | A versão em que as tabelas, a lista de prewarm e as notas do perfil foram feitas. O script do NSP empacota a versão mais nova da pasta (`-p` / `PACKAGE` escolhe outra) |
| `shader_versions` | As versões cuja união as tabelas de shader são (o jogo base primeiro). Uma versão registrada é montada do perfil como está só quando todas elas estão na pasta; senão, de um perfil derivado, com tabelas só da versão empacotada |
| `modules` | Módulos de código reescritos e carregados, na ordem de carga. O `rtld` é substituído pelo host |
| `romfs_marker` | Um caminho que deve existir no RomFS; vazio confere o próprio diretório para um programa sem seção de dados (ANIMAL WELL) |
| `romfs_check <caminho> <linha> <esperado>` | Uma linha de arquivo de RomFS que distingue o RomFS com patch desta versão dos dados de outra versão, onde o `romfs_marker` não consegue (um arquivo que toda versão tem). A `<linha>` conta de 1; o `<esperado>` é o texto da linha, ou `main`: a linha é o começo (16 dígitos hex ou mais) do build ID do `main` para o qual o RomFS é. Linhas podem se repetir. O launcher Android as confere antes do Prepare e no cartão do jogo (`RomfsCheck.java`), para pastas e arquivos `.nup` em qualquer layout. Donkey Kong Bananza: `System/RegionLangMask.txt 4 main` |
| `zip_store` | Extensões que o IPA armazena sem comprimir |
| `mem_reserve`, `mem_alias`, `mem_stack`, `app_pool` | Partição do espaço de endereços do convidado e application pool (`hle_svc.c`) |
| `mem_used` | Memória que o `GetInfo(UsedMemorySize)` reporta além do heap (padrão `0x4000000`, 64 MB). O `SetHeapSize` confere um pedido contra o tamanho real dos módulos carregados, então um jogo que dimensiona seu heap como total − usado e tem mais de 64 MB de módulos precisa de pelo menos o tamanho deles aqui. Hyrule Warriors: Age of Calamity: 66,6 MB de módulos, então o padrão fazia o `SetHeapSize(pool − 64 MB)` falhar e o `nnMain` retornar de imediato; ele põe 72 MB. Cuphead: 80 MB de módulos, 84 MB |
| `sys_resource` | O tamanho de recurso de sistema que o NPDM declara (main.npdm META +0x14), que o `GetInfo(TotalSystemResourceSize)` reporta (`hle_svc.c`). O `IsVirtualAddressMemoryEnabled` do SDK é "esse tamanho não é 0", e alguns jogos escolhem sua configuração de memória por ele: o `nninitStartup` do Big Brain Academy: Brain vs. Brain pede ao StandardAllocator uma região de endereços de 60 GB com memória de endereço virtual e configura um heap sem ela, e seu NPDM não declara nenhuma (`0`). O survey o escreve a partir do NPDM para todo jogo novo; um perfil sem ele obtém a resposta anterior do host, 32 MB, para todo jogo |
| `game_args` | Argumentos que o jogo recebe quando a linha de comando não dá nenhum (o app iOS, as execuções Mac do script do NSP), separados em espaços; `dmhost <dir> -- …` os sobrescreve. O SDK os entrega ao jogo antes do `nninitStartup`, como no hardware (`main.c`). Nenhum perfil define algum agora: a região de engine da Unreal, que `-SwitchVirtualAddressSpaceSize=` dimensionava até 2026-10-31, obtém o que a região alias tem de espaço pelo portão do rewriter (`dm/tools/ue_region.py`) |
| `game_env` | Pares `CHAVE=VALOR`, separados por espaços, que o `getenv` do jogo retorna (`hle_os.c`; qualquer outro nome vai para o `getenv` do próprio SDK, cujo ambiente é vazio como no Horizon). Para runtimes que tiram suas configurações do ambiente. Absolum (.NET NativeAOT) põe `DOTNET_GCRegionRange=60000000`: caso contrário o GC reserva 5 × o limite rígido do seu heap como faixa de região, 3,75 GB, que só a região alias de 64 GB do Switch comporta. O `DM_GAME_ENV` o sobrescreve, também pelo `Documents/env.txt` |
| `fastboot_env` | Chaves `CHAVE=VALOR` do host, separadas por espaços, que `DM_FASTBOOT=1` define para uma execução de teste (`main.c` `fastboot_apply`; uma chave que o ambiente ou o `env.txt` definem vence): a entrada roteirizada e o marcador que levam o jogo à sua cena de teste o mais rápido que ele permite, para que agentes escrevam uma linha em vez de uma lista de toques. Donkey Kong Bananza: A a cada 12 quadros desde a primeira apresentação, um `[mark]` nos seus frames 3D do primeiro nível, e nenhum toque depois disso ([android/TESTING.md](../../android/TESTING.md#fast-test-runs)) |
| `host_env` | Chaves `CHAVE=VALOR` do host (`DM_<NAME>`, separadas por espaços, cada uma uma vez) com que este jogo começa em toda execução (`main.c` `env_defaults`, antes que qualquer coisa leia uma chave, depois das do `DM_FASTBOOT`; uma chave que o ambiente ou o `env.txt` definem vence, e o log nomeia cada uma como `host_env (game profile): CHAVE=VALOR`). Para um jogo que precisa de outro valor que o padrão do próprio host, quando esse padrão agrada aos outros jogos: Ocarina of Time no Android, `DM_VK_PLACE_PART_MB=64 DM_VK_PSO_ASYNC=2` (seus pools de textura de 88-305 MiB colocados por partes, pipelines feitos em segundo plano; sem eles o matador de memória baixa encerrou seu primeiro carregamento de cena) |
| `skip_until_draws` | `<desenhos> [segundos]`: onde o skip de intro (`DM_SKIP`, `hle_hid.c`; [android/TESTING.md](../../android/TESTING.md#intro-skip)) se desliga: tantos segundos depois de 5 quadros apresentados em sequência com aqueles desenhos ou mais, seus primeiros frames de gameplay (o `DM_SKIP_UNTIL` vence). Sem ele, o skip roda até o `DM_SKIP_MAX` ou é desligado à mão. Ocarina of Time: `500 10` (filmes e título têm 2-16 desenhos, Kokiri Forest 647 e mais; 10 s a mais para o primeiro diálogo) |
| `mem_map_limit` | `on` / `off` (o padrão): o `MapPhysicalMemory` falha com ResultLimitReached quando levasse o processo além do application pool (o pool menos a memória usada que o `GetInfo` reporta), como no Horizon (`hle_svc.c`). Pokémon Legends: Z-A aloca e libera tudo o que pode na inicialização e o SDK mantém as páginas liberadas mapeadas até um map falhar, então os desmapeia e tenta de novo; sem o limite elas ficam mapeadas e o jogo mapeia além do pool. Desligado por padrão: Ace Attorney Investigations Collection mapeia um pouco mais que o pool de 1 GB que seu perfil reporta |
| `stdalloc_cap` | Com memória de endereço virtual, o espaço de endereços que o `StandardAllocator::Initialize(nullptr, size)` obtém quando `size` é mais do que a região alias tem de espaço (`hle_svc.c` "StandardAllocator's address space", um portão que o rewriter coloca por símbolo em todo `sdk`). Padrão `0`: o espaço, a região alias menos as regiões já criadas (pelo menos a área de nós de 62 MB) e 256 MB para as regiões criadas depois dela. Necessário quando estas precisam de mais (o coletor de lixo .NET do Absolum leva 1,5 GB depois do seu `malloc`): a checagem de região de endereços do script do NSP o define num perfil provisório ou derivado a partir do que mediu, e confere um valor posto à mão. Um pedido que cabe nunca é mudado |
| `present_interval` | `game` (o padrão): os quadros são ritmados pelo intervalo de apresentação que o jogo define, como no Switch (um quadro apresentado com intervalo 2 fica na tela por dois ticks de display; um jogo que continua pedindo 2 por um segundo obtém o alvo de 30 fps, e no iOS o display link roda então a 30 Hz; Mario 1.2.1 troca para 2 por quadros isolados depois de um lento; Engage pede 2 no Switch, e um corte do rewriter no seu `main` 2.0.0 faz ele pedir 1, veja `0100A6301214E000/game.tsv`). `display`: um quadro por tick de display seja o que for que o jogo peça, o que só é certo para jogos cuja lógica não conta quadros (as corridas do D2R seguem seu próprio relógio de 25 Hz; Monster Train 2 pede 2 e avança pelo tempo de quadro do Unity, então roda a 60 fps: capturas nos mesmos momentos coincidem a 30 e 60 fps). O `DM_PRESENT_INTERVAL=game` / `display` o sobrescreve, também pelo `Documents/env.txt` |
| `present_snap` | `on` / `off` (o padrão): snapshots de apresentação por padrão (`nvn_mtl.m` `mtl_snap_on`, um anel de 2 texturas do host): cada apresentação é copiada e a textura de swapchain do jogo fica livre de imediato, então o GPU não fica ocioso entre quadros ([Snapshots de apresentação](../../docs/reference/frame-rate.md#present-snapshots-the-games-swapchain-texture-free-at-once)). Uma configuração com que o jogo foi testado: o **Frame buffering** do launcher iOS tem ela como padrão, e `DM_PRESENT_SNAP` / `Documents/env.txt` a sobrescrevem. Breath of the Wild a liga |
| `pso_mtl4` | `on` / `off` (o padrão): no iOS, render pipelines pelo MTL4Compiler por padrão, com o arquivo de pipelines, o passo de prepare, os pipelines híbridos e o prebuild (ligado por padrão no Mac; `DM_PSO_MTL4=1` / `0` sobrescreve). Uma configuração com que o jogo foi testado num iPhone. Ela também dá ao app o [arquivo de pipelines feito offline](../../docs/development.md#the-pipeline-archive-made-offline) (o `build_ipa.sh` o monta para a lista da chave `pso_gpu` quando presente, senão para `g18p`, a menos que o `DM_PSO_GPUS` diga o contrário) e as bibliotecas de pull (`_bp`). Perfis com `pso_mtl4 off` não recebem arquivo a menos que um override de build selecione um. Breath of the Wild liga isto |
| `pso_gpu` | Opcional, arquiteturas de GPU separadas por espaço: aquelas para as quais o [arquivo de pipelines feito offline](../../docs/development.md#the-pipeline-archive-made-offline) é feito quando o perfil também põe `pso_mtl4 on`. As bases são feitas por família de GPU e o arquivo de cada família custa sua própria execução de `metal-tt`, então um perfil nomeia exatamente os dispositivos que atende. 1-4 tokens, cada um alfanumérico, com ou sem o prefixo `applegpu_` (por exemplo `g18p applegpu_g19p`); `none` não é um valor. Sem esta chave, `pso_mtl4 on` mantém o padrão A19 / A19 Pro `g18p`; `pso_mtl4 off` não recebe arquivo. A chave `DM_PSO_GPUS` / o `--gpu` do script do NSP sobrescreve a seleção do arquivo; esta chave não habilita pipelines Metal 4 |
| `enc_thread` | `on` / `off` (o padrão): no Mac, a codificação Metal na sua própria thread por padrão, como no iOS para todo jogo (`nvn_rec.h` `rec_on`; o `DM_NVN_ENC_THREAD=1` / `0` e o Encode thread do launcher o sobrescrevem). Para um jogo que espera sua fence a cada quadro, cuja thread de submissão teria também que codificar antes da espera: o quadro de 60 fps do Need for Speed: Hot Pursuit Remastered levou 18,1 ms com a codificação na thread de submissão e 16,7 na sua própria |

### Linhas de prontidão

O `readiness.tsv` (opcional, Android): o que o jogo exige de um celular, para a [checagem de prontidão](../../android/README.md#verificacao-de-prontidao) do launcher. Uma tabela própria em vez de chaves do `game.tsv`: as linhas do launcher ficam separadas das do host. (A chave de reescrita de um pack, `pack_android.py` `rewrite_key`, hashia só as linhas `build` do `game.tsv`, então outras linhas não tornam packs obsoletos.) Separado por tabs, comentários com `#`; o `build.gradle` entrega as linhas ao launcher (`BuildConfig.NX_PROFILES`, `Profile.reqs` / `status`).

| Linha | Significado |
|---|---|
| `status <playable\|bring-up>` | O estado do jogo no Android. `bring-up` mostra um aviso em todo celular (pode parar ou desenhar errado em qualquer lugar) |
| `required <fato> <no mínimo> <título>: <motivo>` | Sem ele o jogo não roda, para, ou não desenha nada do que precisa dele: a tela inicial mostra **Este celular não tem o que este jogo precisa** com **Tentar mesmo assim** |
| `degraded <fato> <no mínimo> <título>: <motivo>` | O jogo roda sem ele, com algo faltando ou em detalhe menor: um aviso que o usuário pode desligar |

Um fato é uma chave do `nxhost_vk_readiness` (`dm/gfx/vk_android/vka_readiness.c`: `vk.api`, `feature.<membro de VkPhysicalDevice*Features>`, `limit.<limite>`, `ext.<extensão>`, `sparse.residencyImages`, `sparse.format.<formato>`, `memory.deviceLocalMiB` …) ou do launcher (`ram_gib`: o `totalMem` do ActivityManager em GiB, que fica abaixo do rótulo do celular; `android.sdk`). O mínimo é um número, hex `0x` ou uma versão pontuada; um fato que o driver não reporta conta como ausente. Várias linhas podem nomear um fato (um piso de memória `required` e uma quantidade testada `degraded`); uma linha `degraded` de um fato cuja linha `required` falhou não é mostrada. Escreva só o que o código ou os shaders do jogo mostram que ele precisa, com a evidência num comentário (`android/SHADERS.md`, `shader_facts.tsv`, a nota); uma limitação do port em vez do celular (shaders que o tradutor ainda não faz) não é uma linha. O `dm/tools/tests/test_android_readiness.py` verifica que toda linha nomeie um fato que é reportado.

### O que os arquivos do jogo decidem a cada build

Estas não são chaves de perfil: as ferramentas as leem dos arquivos do jogo a cada vez, por regras conferidas contra todo perfil (`dm/games/profile_guess.py` `shader_sources`).

- **API gráfica.** Um jogo cujo `main` importa funções Vulkan e não o `nvnBootstrapLoader` renderiza com Vulkan, que o host implementa sobre Metal (`dm/gfx/vk/hle_vk.m`; Hades, Super Mario Galaxy). Seus shaders são seus arquivos SPIR-V, traduzidos pelo `dm/gfx/tools/vk_shaders.py <RomFS> <pasta de shader> [--ios <pasta>]` para `<pasta>/vk/`, e o `build_ipa.sh` leva `$MSL_IOS/vk` em vez das bibliotecas da cadeia NVN (`GFXAPI`, que o script do NSP passa; à mão, as bibliotecas de shader ali dizem). As tabelas de shader NVN ficam vazias.
- **SPIR-V gerado em tempo de execução.** Um jogo Vulkan sem arquivos SPIR-V no seu RomFS gera seus shaders em tempo de execução (Super Mario Galaxy: os shaders GX do Hagi, 3.089 módulos criados a partir do seu banco de dados de pipelines enquanto mostra "Initializing system..."). O script do NSP os captura no Mac com `DM_VK_CAPTURE=<pasta>` (`dm/gfx/vk/hle_vk.m`), subindo o jogo no host Mac até que toda chave listada no `vk_capture.tsv` do perfil esteja lá, e o `vk_shaders.py` traduz a pasta capturada junto com o RomFS. Um jogo OpenGL sem fonte GLSL no seu RomFS ou `main` (Balatro: o LÖVE monta seus shaders em Lua) é capturado do mesmo jeito com `DM_GL_CAPTURE=<pasta>` (`dm/gfx/gl/hle_gl.m`) até que todo arquivo do `gl_capture.tsv` esteja lá, e o `gl_shaders.py` traduz a captura.
- **Shaders compilados em tempo de execução.** Um jogo que chama `glslcCompile` num módulo que carrega, com fontes GLSL em `main` (Fire Emblem: Three Houses: 9 shaders KTGL embutidos na inicialização) ou, sem nenhuma ali, arquivos `.vert` / `.frag` no seu RomFS (Turrican Anthology), compila alguns shaders em tempo de execução com seu próprio GLSLC, então nenhum arquivo do jogo os contém. O script do NSP os captura no Mac com `DM_GLSLC_CAPTURE=<pasta>` (`dm/host/hle_glslc.c`), subindo o jogo no host Mac até que todo arquivo de captura nomeado pelo `shader_map.tsv` do perfil esteja lá, e o `shader_split.py` lê `<pasta da versão>/glslc_capture/*.glslc` (ao lado do `RomFS` daquela versão) ou `$DM_GLSLC_CAPTURE`; sem a pasta ele imprime uma linha vermelha, aqueles shaders não recebem tradução e as tabelas diferem das do perfil.
- **Paks da Unreal.** Um jogo Unreal Engine guarda seus shaders nos arquivos de código de shader dos seus paks (`*.ushaderbytecode`; um pak é da Unreal quando seu rodapé tem a magic da Unreal, `uepak.py` `unreal_paks`), cada shader comprimido com Oodle, que só o Oodle do próprio jogo descomprime. O script do NSP (`decode_ue_shaders`) tira os arquivos dos paks com `dm/gfx/tools/uepak.py` (o índice do pak está criptografado com AES com uma chave que ele acha em `main`), sobe o jogo no host Mac com `DM_OODLE_JOB` (`dm/host/hle_oodle.c`: o `OodleLZ_Decompress` do jogo, encontrado como a única função que referencia a string do nome da própria biblioteca, decodifica todo shader logo antes do `nnMain`, e então o host sai) e escreve os arquivos decodificados em `<pasta da versão>/ue_shaders`, de onde o `shader_split.py` os lê (o `DM_UE_SHADERS` sobrescreve; sem eles ele para). Octopath Traveler 0: 10.596 shaders em 2 s. Unreal Engine 4.26 e depois comprimem shaders com LZ4 a menos que o projeto escolha outro formato (DRAGON QUEST VII Reimagined, 4.27: 64.949 shaders, seus pacotes em contêineres IoStore ao lado do pak); o `uepak.py` os decodifica sozinho (`lz4_shaders`) e o script do NSP pula a execução do host. Um pak cujo índice lista pacotes cozidos e nenhum `.ushaderbytecode` (`uepak.py` `inline_shaders`: paks legados de versão 4, e o pak de versão 11 do OCTOPATH TRAVELER II com `bShareMaterialShaderCode` desligado) guarda seus shaders inline nos pacotes; o `shader_split.py` os lê arquivo por arquivo (`ue_legacy_jobs`) e o script do NSP não decodifica arquivo algum.
- **Packs Trinity.** O motor Trinity da Game Freak guarda quase todo arquivo em packs comprimidos com Oodle (`arc/data.trpfs`, arquivos começando com `ONEPACK`; Pokémon Legends: Z-A). O `shader_split.py` os decodifica com o `OodleLZ_Decompress` do próprio jogo, executado pelo host Mac no seu modo de ferramenta (`dm/host/hle_oodle.c`, `DM_OODLE_SERVE`). A divisão exige `DM_OODLE_HOST` (o host Mac) e `DM_OODLE_MODULES` (os módulos reescritos); o script do NSP monta o host e define ambos quando a divisão roda.
- **Saídas GLSLC em `main` e arquivos soltos.** O `shader_split.py` lê saídas do compilador GLSLC (magic `0x19866891`, cada uma conferida inteira) em todo `main` de jogo: 13 Sentinels e Unicorn Overlord guardam todos os seus shaders ali, os jogos KTGL alguns; o player do Unity tem 11 próprios ao lado dos shaders do jogo nos seus bundles (Engage, Ace Attorney Investigations Collection). Ele os lê também em qualquer arquivo de RomFS que nenhum outro leitor pegue: FINAL FANTASY TACTICS - The Ivalice Chronicles guarda 257 nos seus arquivos de técnica (`resources_nx/release/master/shader/*.tec`), Absolum (FNA3D) 163 em `shaders.nx.bin`.
- **Efeitos MonoGame.** O `shader_split.py` lê os efeitos MGFX do MonoGame onde quer que estejam (`mgfx_effect`): Celeste guarda 13 nos seus arquivos XNB (`Content/Effects/*.xnb`) e o embutido do SpriteBatch está em `main`.
- **Programas de estágio único.** Uma saída GLSLC, um registro de shader Unreal ou o shader de um efeito MonoGame é um programa de um estágio, combinado com outros por desenho (uma pass do MonoGame pode não nomear vertex shader algum e manter o do SpriteBatch), então seus pares reais de vertex / pixel só existem em tempo de execução. O `shader_split.py` pareia cada vertex shader assim com uma cobertura de pixel shaders que juntos leem toda entrada que qualquer pixel shader leia, e o `vs_pad` do `dmsh_build.py` faz linkar com qualquer pixel shader (13 Sentinels, Unicorn Overlord, os jogos KTGL, Octopath Traveler 0, Celeste). Variações BNSH, programas Unity e os arquivos MSHD e SDF pareiam seus próprios shaders.
- **Tabelas do driver NVN.** Os segmentos de constantes do driver têm um layout em todo jogo (`dmsh_build.py`, preenchido pelo `nvn_mtl.m`): o c2 guarda os handles vinculados com `nvnCommandBufferBindTexture` em `0x20 + 8 × slot`, imagens em `0x120 + 8 × slot`, texturas separadas em `0x168 + 8 × slot` e samplers separados em `0x568 + 8 × slot`; o c0, as tabelas de storage buffer (vertex 0x110, compute 0x310, pixel 0x510). Binds de textura separada são os slots de textura 128 + n da tabela do host (`NVN_SEPTEX_SLOT0`), então um jogo pode vincular ambos os tipos num mesmo quadro (Monster Hunter Rise: slot combinado 0 ao lado de slots separados 0-4), e um slot combinado além de 31 (Hades II vincula o slot 34) fica na tabela de imagens, onde uma textura vinculada vence uma imagem não vinculada. O tradutor (`dmsh_xlate/Program.cs`) numera os slots do mesmo jeito quando procura tipos de textura / imagem por slot em `shader_facts.tsv`.

## Adicionando um jogo

1. **Survey.** Rode `scripts/build_ipa_from_nsp.py` na pasta NSP do jogo. Sem perfil, ele extrai só os módulos de código e uma lista de RomFS, e escreve `<pasta NSP>/<title ID>_survey/survey.md`. O survey cobre módulos e build IDs, SDK, engine e marcadores de API gráfica, contêineres de RomFS, o censo de pontos de reescrita, e imports comparados com os hooks do host.
   Salvo ordem `--survey-only`, o script então escreve um **perfil provisório** em `<pasta NSP>/<title ID>_build/profile/<title ID>/` (fora do repositório) e segue até um IPA de melhor esforço. O `dm/games/profile_guess.py` preenche seu `game.tsv` a partir dos arquivos do jogo, cada chave sob o motivo dela (o survey também os lista):
   - identidade e nome, a linha de build que encontrou, o maior arquivo de RomFS como `romfs_marker`, tipos de arquivo grandes em `zip_store`, `shader_groups` pelas pastas de topo do RomFS;
   - `modules`: um subsdk é carregado só quando `main` importa algo dele que o host não forneça ele mesmo, ou, quando o estágio de reescrita já coletou os NROs do jogo, quando um deles importa (`nro_modules`: os NROs da Source engine de Portal usam o módulo de filme e o GLSLC, que o seu `main` não usa). Sob a camada Vulkan o carregador Vulkan e o GLSLC são descartados; módulos de filme e um GLSLC que `main` chama ficam. Os drivers OpenGL e Vulkan da NVIDIA nunca são carregados: eles programam o GPU através de NvRm, que o host não tem (Absolum importa EGL para o suporte GL do SDL3 e renderiza com NVN);
   - a partição de memória. Sem recurso de sistema no NPDM: o layout de 4 GB, sua região de heap o pool − 64 MB − o bss de módulos gigantes (Metroid Dread: 0x90000000). Quando `main` nunca configura um heap: um bloco de 1 GB (Super Mario Galaxy). Com um recurso de sistema: o bloco de 5 GB do Engage com o pool do hardware, que a checagem de heap corrige quando o jogo configura um heap (sem um, o jogo mapeia tudo na região alias ele mesmo: Hollow Knight: Silksong, Absolum, Pokémon Legends: Z-A);
   - Predefinições de engine: Hagi (`hagi.config`) recebe `op_mode handheld` e `pad_layout full`.

   `python3 dm/games/profile_guess.py --check` aplica essas regras a todo perfil em `dm/games` (com as extrações sob `/Volumes/T7/nsp`) e lista as chaves em que o palpite difere.

   Depois da reescrita, o `mem_used` é definido quando os módulos reescritos passam dos 64 MB padrão (um jogo sem recurso de sistema); mantenha-o quando o perfil entrar em `dm/games` (Cuphead sem ele: um heap de 0,03 GB e um abort na primeira alocação). Um jogo com recurso de sistema que configura um heap então recebe uma **checagem de heap**: ele sobe no host Mac (headless, sem bibliotecas de shader) até seu primeiro pedido de heap, ou 5 s dentro de `nnMain` sem um, no máximo 30 s (`HEAP_CHECK_SECS`). Um pedido que a região de heap não comporta (`SetHeapSize OOM`) define a divisão alias / heap (Tears of the Kingdom pede 0x86000000, o que dá sua região alias feita à mão de 0x98000000; os 1,44 GB de Wonder dão 0xc0000000), e uma checagem de pool que falha definitivamente define `mem_used`. Uma execução sem heap configurado cuja região alias fica usada até dentro de 0,25 GB do seu fim define um pool de 1 GB: o `nninitStartup` entregou pool − usado ao StandardAllocator como uma região de endereços e o jogo reserva regiões próprias ao lado dela (Unity 2020 e 2022: AI: THE SOMNIUM FILES - nirvanA Initiative chegou a +4,26 GB de 4,38 em 5 s com o pool do hardware; o Raging Loop do Unity 2018.3 mapeia só dentro da região do StandardAllocator e a mantém). O GB é um ponto de partida, não uma medição: Advance Wars 1+2: Re-Boot Camp (Unity 2020.2) secou seu malloc na sua primeira tela de carregamento com ele e precisa de 2 GB. O perfil recebe uma linha `# heap check:`, e execuções seguintes mantêm suas chaves (apague a linha para conferir de novo; `--no-heap-check` / `HEAP_CHECK = False` pula). Outros jogos pulam a checagem, então ela não custa nada para eles e alguns segundos mais um build do host Mac para o resto.

   Nenhuma execução curta decide `render_cond`, `tex_flush_upload`, `tex_dirty_upload`, `core_preempt`, `gpu_timestamps`, `vconv_range` nem `present_interval`, nem `op_mode` / `pad_layout` fora das predefinições: eles ficam com seus padrões para um desenvolvedor. Um minuto de boot sem entrada contou os clears do Wonder sob condições de render (65.536 ou mais; ele não precisa de `render_cond`) tão prontamente quanto os de Tears of the Kingdom, viu Breath of the Wild purgar 32 texturas preenchidas pela CPU com dados (ele não precisa de `tex_flush_upload`) e Age of Calamity nenhuma (seus quadros de filme vêm depois), e o crash de filme do Metroid Dread no host antigo aparecia em cerca de metade das execuções (agora resolvido por [passagens de wake compartilhadas](../../docs/reference/threads.md#same-core-wake-handoffs)). No iPhone, o `Documents/env.txt` ainda pode definir `DM_OPMODE`, `DM_NVN_GPU_TS` e `DM_NVN_FB_SNAP`, e o layout do gamepad muda no jogo.

   As tabelas de shader, `c1_full.tsv` e `cb_extent.tsv` são escritas na mesma pasta. Uma segunda execução reutiliza aquele `game.tsv` (apague-o para pesquisar de novo), então ele pode ser editado à mão. O `--provisional` monta a partir de um perfil provisório mesmo para um jogo que tem um em `dm/games`, para testar os palpites: o `DM_GAMES_FIRST=1` faz toda ferramenta procurar em `DM_GAMES_DIR` primeiro, e o IPA recebe `-provisional` no nome. As ferramentas encontram perfis fora de `dm/games` através de `DM_GAMES_DIR` (pastas separadas por `:`, procuradas depois de `dm/games`); o `make -C dm/host` alcança um perfil assim pelo symlink `dm/host/gen/<id>/profile`. Para ficar com um jogo, mova a pasta para `dm/games/` e faça o bring-up como abaixo.
2. **Perfil.** Copie o `game.tsv` de um perfil (para um jogo Switch 2, `040074A01BF12000/game.tsv`; ou o perfil provisório) para `dm/games/<title ID>/game.tsv` (o title ID do jogo base, como o nome da pasta) e preencha a identidade, as linhas `build` e os `modules`. Deixe os valores de memória como os de Mario até o bring-up medi-los ([docs/agents](../../docs/agents/README.md)).
3. **Tabelas de shader.** Rode `DM_GAME=<id> shader_split.py … dm/games/<id>/shader_map.tsv dm/games/<id>/shader_facts.tsv dm/games/<id>/shader_pairs.tsv dm/games/<id>/pso_pairs.tsv`. Acrescente um `shader_map.tsv.conflicts.tsv`, `bf_want.tsv` e `pso_manifest.tsv` vazios (copie os cabeçalhos de Mario).
4. **Shaders.** `DM_GAME=<id> [IOSOUT=…] dmsh_build.py <pacote> <cache>`, com um diretório de cache próprio do jogo. Um build completo também escreve `c1_full.tsv` e `cb_extent.tsv` (arquivos locais, não commiteados). A versão da cadeia não precisa de nada: é a mesma para todo jogo.
5. **Bring-up do host.** Rode `make -C dm/host GAME=<id>`, depois percorra o ciclo de bring-up em docs/agents. Código que só serve a um jogo é portado pelo seu build ID (`dm_main_build()`), nunca deixado para rodar em todo jogo.
6. **IPA.** Use `GAME=<id> dm/ios/tools/build_ipa.sh`, ou o script do NSP, que agora encontra o perfil.
