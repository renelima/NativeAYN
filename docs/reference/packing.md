# Empacotamento

## Ferramentas de build

### O .NET do Homebrew está no PATH mas os apphosts não conseguem achar o runtime

- **Sintoma:** a primeira extração para com `nx_extract exit code 131` e `.NET location: Not found`, mesmo com o `dotnet` no `PATH`. O tradutor de shaders pode falhar do mesmo jeito.
- **Causa:** os apphosts de .NET standalone procuram raízes de runtime e instalações registradas, não o `PATH` ([descoberta de runtime do .NET](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-environment-variables#dotnet_root-dotnet_rootx86-dotnet_root_x86-dotnet_root_x64)). A fórmula do Homebrew instala o runtime sob `libexec` e o `bin/dotnet` dela pode ser um wrapper que define o `DOTNET_ROOT` só para o próprio filho ([aviso do Homebrew](https://formulae.brew.sh/formula/dotnet)). Resolver o symlink desse wrapper dá `bin`, não a raiz do runtime.
- **Correção:** o `configure_dotnet` de `scripts/build_ipa_from_nsp.py` deriva a raiz da entrada `Microsoft.NETCore.App` em `dotnet --list-runtimes`, usando o ambiente da build, antes de qualquer extração ou survey. Ele exporta o `DOTNET_ROOT` tanto para esse ambiente quanto para `os.environ`, para ferramentas iniciadas com um ambiente explícito e as que o herdam. As raízes fornecidas pelo chamador, incluindo overrides específicos de arquitetura, mantêm precedência. Uma sondagem que falha ou é malformada deixa o ambiente inalterado em vez de adivinhar o diretório do wrapper.
- **Encontrado em:** Balatro, primeira extração com o .NET do Homebrew ([PR #284](https://github.com/seedds/nxnative/pull/284)). Vale para a build de todo jogo naquela configuração de instalação.

### O passo de shaders para com um `xlate_source` vazio

- **Sintoma:** a extração e as capturas têm sucesso, depois o passo de shaders para com `translation chain tools do not match the lock file: xlate_source: lock … / actual` e nada depois de `actual`, o que parece um tradutor desatualizado.
- **Causa:** o tradutor (`dmsh_xlate_bin/dmsh_xlate`) é um apphost universal dependente de framework. Quando não acha um runtime .NET 10 para o slice com que ele inicia, sai com 131 e stdout vazio. Um Python sob Rosetta (de um Homebrew Intel) o inicia como x86_64, e ele acha só o .NET arm64; a extração não é afetada, porque o `nx_extract` é compilado só para a arquitetura do próprio SDK. Um .NET Intel no Apple silicon, ou um `DOTNET_ROOT` que nomeie um, falha do mesmo jeito. O `tools_now` (então em `dmsh_chain.py`) guardava só o stdout do `dmsh_xlate --source-sha`, sem o código de saída nem o stderr, então a mensagem própria do apphost se perdia.
- **Correção:** o script do NSP confere o ambiente antes de extrair qualquer coisa: o `check_native_python` para sob Rosetta (`sysctl.proc_translated`), e o `check_prereqs` inicia o tradutor uma vez com `--source-sha` e para com a primeira linha de mensagem dele (`check_translator`). Ele também confere o glslang e, para uma build de iPhone, o iOS SDK (`check_ios_sdk`, antes da checagem do Metal, cuja mensagem culparia o toolchain do Metal). O `own_compilers.py` não pede mais a uma build de shaders só de Mac (`DMSH_TARGETS=mac`) o compilador Metal do iOS. O `tool_lock.py` registra a falha do `--source-sha` em vez do seu stdout vazio (`xlate_embedded`: `does not run (<first message line>)`), então o `dmsh_build.py` rodado direto e o `--update-lock` param com a mesma mensagem que o script do NSP, sem as linhas de lock e rebuild. As checagens de ferramentas ficavam antes no `dmsh_chain.py`, que faz parte da versão da chain e da cache key de todo shader, então aquela correção recompilava toda biblioteca; elas agora ficam no `tool_lock.py`, fora de ambas, e uma mudança nelas não recompila nada.
- **Encontrado em:** builds do NX2Apple ([LNPANDY/NX2Apple#31](https://github.com/LNPANDY/NX2Apple/issues/31), item 3; [PR #477](https://github.com/seedds/nxnative/pull/477), [PR #487](https://github.com/seedds/nxnative/pull/487)); reproduzido com `arch -x86_64`. Vale para todo jogo.

## Arquivos IPA

### Um arquivo em stream muda de tamanho e o IPA falha na checagem de CRC

- **Sintoma:** o empacotamento tem sucesso, mas o `unzip -t` ou o `ZipFile.testzip()` do Python reportam um CRC ruim para um arquivo grande deflated.
- **Causa:** o `pack_ipa.py` escrevia o tamanho descomprimido coletado antes de ler. A sua checagem em stream comparava o tamanho de saída só para arquivos stored, então um arquivo comprimível que crescia ou encolhia ainda publicava um arquivo com o tamanho antigo.
- **Correção:** conte os bytes descomprimidos conforme são lidos e compare-os com o tamanho listado antes de completar qualquer um dos métodos em stream. Uma divergência para o pack e remove o arquivo parcial, preservando o IPA anterior e o seu índice de reuso. Testes de regressão cobrem crescimento e encolhimento com deflate e store.
- **Encontrado em:** entradas de IPA sintéticas ao revisar o [PR #279](https://github.com/seedds/nxnative/pull/279); nenhum arquivo de jogo é necessário.

## Imagens de RomFS

### Transferências de pasta de RomFS falham ou deixam arquivos de jogo obsoletos

- **Sintoma:** o `devicectl` copiando uma pasta de RomFS grande falha com o erro POSIX 24 (`EMFILE`) ou gasta a maior parte do tempo em arquivos pequenos; apagar uma pasta antiga durante a inicialização do iOS esbarra no watchdog de lançamento. Um push depois de mudar arquivos extraídos também pode continuar mandando assets antigos se uma imagem é reusada só porque existe.
- **Causa:** uma transferência de pasta realiza centenas de milhares de operações de arquivo. O cache de imagens precisa rastrear a sua árvore de origem, e o magic mais o comprimento total não podem estabelecer que o índice de uma imagem é válido. Aceitar aquela checagem fraca antes de apagar a pasta de trabalho perde o fallback quando a montagem depois rejeita o índice.
- **Correção:** o `dm/tools/romfs_image.py` empacota um arquivo `DMROMFS1`: um cabeçalho de 32 bytes, os bytes dos arquivos, depois o índice e o pool de nomes. Cada diretório tem uma sequência contígua ordenada de entradas filhas; o host faz busca binária em cada componente do caminho e lê faixas de arquivo com `pread` por meio de um descritor por montagem. Pastas de overlay mantêm precedência e as listagens de diretório mesclam ambas as fontes. O carregador compartilhado `dm/host/romfs_image.h` confere o índice completo antes tanto da montagem quanto da limpeza de pasta do iOS: comprimento, limites de entrada e de nome, faixas de arquivo, uma árvore de diretórios enraizada em busca em largura, e nomes de filha ordenados e únicos. Ele também suporta uma raiz vazia. Imagens inválidas recorrem às pastas no iOS; uma imagem `DM_ROMFS` explícita inválida é recusada com uma linha `[RED]`. A checagem do índice detecta transferências sequenciais interrompidas e dano estrutural, não corrupção de mesmo comprimento dentro do conteúdo dos arquivos. O empacotador publica por renomeação só depois que a fonte fica estável. O seu selo de reuso rastreia nomes de origem e metadados de arquivo incluindo ctime, o empacotador e a identidade da imagem; o ajudante de push sempre o confere, e o `--repack` força uma rebuild. Uso: [Reinstalações rápidas](../development.md#quick-reinstalls).
- **Encontrado em:** Tears of the Kingdom, cuja transferência de 304.000 arquivos e falhas de apagar na inicialização são reportadas no [PR #369](https://github.com/seedds/nxnative/pull/369). ANIMAL WELL dá o caso de boot de imagem vazia. Testes sintéticos de empacotador/host cobrem leituras reais de arquivos, aliases de maiúsculas/minúsculas, mesclagem de overlay, índices corrompidos e fontes alteradas; o teste de Foundation do macOS executa o localizador do iOS para conferir que imagens rejeitadas preservam a pasta dele.

### Um caminho `DM_ROMFS` obsoleto derruba o jogo logo depois de `nnMain`

- **Sintoma:** uma execução direta do `dmhost` registra `fs mount rom: → <path> (read-only)` para um caminho que não existe, depois derruba no código do jogo uma fração de segundo depois de `nnMain` (Echoes of Wisdom: `CRASH sig=11 addr=0x88` aos 0,3 s). Agora o host para na montagem em vez disso com `FATAL the game files <path> (rom:) are missing: neither a folder nor a RomFS image`.
- **Causa:** um comando de execução antigo ainda nomeava a pasta `RomFS` da extração depois que uma reconstrução a substituiu por `RomFS.img` ([Transferências de pasta de RomFS](#transferencias-de-pasta-de-romfs-falham-ou-deixam-arquivos-de-jogo-obsoletos)). A montagem somente-leitura aceitava qualquer caminho, então toda leitura falhava e o jogo usava os dados que faltavam. O app de iOS e o launcher do app de Mac conferem os arquivos de jogo deles antes de iniciar o host; execuções diretas não tinham essa checagem.
- **Correção:** o `mount_ex` (`dm/host/hle_fs.c`) para numa montagem somente-leitura que não é de save cujo caminho não é nem uma pasta nem um arquivo regular, com o mesmo `stat` que distingue uma imagem de uma pasta. Conteúdo de add-on e dados de sistema conferem os caminhos antes de montar, então só a montagem do rom (`DM_ROMFS`, ou `$DM_ROOT/romfs` quando ele não está definido) chega até ele. O `dm/host/tests/t_fs.c` confere um caminho ausente e um fifo num filho bifurcado.
- **Encontrado em:** Echoes of Wisdom 1.1.0 no Mac ([issue #615](https://github.com/seedds/nxnative/issues/615), [PR #616](https://github.com/seedds/nxnative/pull/616)).

### A implantação de RomFS separada perde a imagem ou o fallback de pasta

- **Sintoma:** uma build `--romfs separate --no-keep-extracted` bem-sucedida imprime um comando de push apontando para arquivos de jogo apagados. No iOS, uma imagem completa de outra build também pode impedir a inicialização apesar de uma pasta `Documents/romfs` válida.
- **Causa:** o modo separado omitia a checagem de reter a extração, então a limpeza normal pós-build apagava a imagem necessária para a transferência. A rejeição de identidade na inicialização retornava antes da busca de pasta existente.
- **Correção:** rejeite o modo separado sem `--keep-extracted` antes de extrair ou compilar. Rejeite uma imagem divergente continuando até o fallback de pasta validado; afaste uma pasta para exclusão só depois de aceitar a imagem. Imagens coincidentes e a rota empacotada padrão mantêm o comportamento. A identidade cobre tamanho, cabeçalho e índice da imagem, não mudanças de conteúdo de arquivo de mesmo comprimento.
- **Encontrado em:** testes sintéticos de CLI e de inicialização de Foundation ao integrar o [PR #493](https://github.com/seedds/nxnative/pull/493), depois do [PR #478](https://github.com/seedds/nxnative/pull/478); nenhum jogo nem dispositivo é preciso para reproduzir qualquer uma das falhas.

### Um RomFS.img copiado à mão não é achado no iOS

- **Sintoma:** um app `--romfs separate` cuja imagem foi copiada para a pasta Documents à mão (Finder, o app Arquivos, um convidado do LiveContainer) registra `boot: game files not found (Documents/romfs.img, Documents/romfs or <App>/romfs)`, e uma build com `romfs.id` mostra "There is no game file image on this device.", embora a imagem completa esteja lá. Renomeá-la para `romfs.img` faz o jogo iniciar.
- **Causa:** o script do NSP grava a imagem como `extract/<version>/RomFS.img`, e o `push_romfs.sh` a copia para `Documents/romfs.img`. Uma cópia à mão mantém o nome da origem. O sistema de arquivos do Mac ignora maiúsculas/minúsculas, então a divergência nunca aparece lá, mas o do iOS não, e o `main.m` procurava só o `romfs.img` exato.
- **Correção:** o `main.m` (`romfs_document_images`) lista Documents procurando `romfs.img` em qualquer caixa de letras, o `romfs.img` em si primeiro, e pega o primeiro que for completo e passar na checagem do `romfs.id`; um rejeitado ou incompleto cai para a grafia seguinte, depois para as pastas. O relatório de identidade, a exclusão do backup e as linhas do log usam os nomes encontrados. Nomes de pasta (`Documents/romfs`) ainda são casados exatamente.
- **Encontrado em:** South Park: The Fractured But Whole 1.05 (`01008F2005154000`, sem profile aqui) num iPhone 15 Pro Max, [issue #582](https://github.com/seedds/nxnative/issues/582). O teste de inicialização de Foundation roda o localizador numa imagem de disco APFS sensível a maiúsculas/minúsculas.

### Compilar cria uma árvore RomFS completa antes de empacotar a imagem

- **Sintoma:** reduzir a transferência do iPhone a uma imagem ainda cria milhares de arquivos de recurso no Mac, e os scanners de build exigem a pasta expandida.
- **Causa:** a extração de pasta seguida de um empacotamento de imagem separado duplica o trabalho; as APIs comuns de sistema de arquivos não conseguem endereçar arquivos dentro de uma imagem.
- **Correção:** o pipeline do NSP passa `--romfs-image` ao `nx_extract`. O LibHac sobrepõe o update ao base e confere a integridade dele enquanto o gravador envia os bytes dos arquivos em stream para uma imagem `DMROMFS1` temporária, acrescenta o índice de diretório ordenado e publica por renomeação. O ExeFS continua expandido; RomFS e cada DLC continuam um arquivo físico. O `dm/tools/romfs.py` dá aos scanners caminhos virtuais somente-leitura, seeks limitados e mapeamentos de arquivo (Python 3.12+), sem mudar as APIs de sistema de arquivos padrão do processo. O empacotador de IPA mapeia a imagem física para `Payload/DmIOS.app/romfs.img`; o iOS e o launcher do Mac validam e montam no lugar. Nem a instalação nem a inicialização expandem os arquivos de recurso. Substituições de Documents e entradas de pasta legadas continuam suportadas. Uma imagem de origem é descomprimida; o IPA pode deflatá-la, então a redução de contagem de arquivos não implica um número menor de bytes instalados. Imagens completas para versões separadas do jogo não podem compartilhar arquivos individuais inalterados por clones do APFS como a extração de pasta legada fazia.
- **Encontrado em:** ANIMAL WELL, cuja imagem direta é uma raiz vazia (56 bytes); a build provisória local do Baba Is You exercita 6.374 arquivos numa imagem de 103.473.292 bytes, 131 shaders e um IPA sem assinatura contendo só a entrada de imagem única. Raging Loop dá recursos do Unity: as 1.473 entradas de manifesto de origem batem com a imagem, e todo shader registrado continua na varredura. Testes de integração sintéticos chamam o gravador LibHac real, leem faixas de arquivo desalinhadas, e exercitam o mapeamento de IPA, o staging do Xcode e a inicialização com imagem empacotada.

### O comando zstd recebe um caminho dentro da imagem

- **Sintoma:** o script do NSP para na divisão de shaders de um profile registrado com `[RED] 13744 file(s) could not be read, their shaders are left out (first: AI/FileEntry/FileEntry.Product.100.byml.zs: CalledProcessError: Command ['zstd', '-d', '-c', '-q', '…/extract/v0/RomFS.img/AI/…'] returned non-zero exit status 1.)`.
- **Causa:** o `unzs` do `shader_split.py` lia um arquivo `.zs` através do `romfs.open`, que lê dentro da imagem, mas depois passava o caminho dele ao comando `zstd`, que só consegue abrir arquivos reais (`Not a directory`).
- **Correção:** o `unzs` alimenta o comando com os bytes que leu (`input=`). Nenhuma outra ferramenta passa a um comando externo um caminho dentro da imagem. Teste: `test_zstd_file_inside_an_image` do `test_romfs_read.py`.
- **Encontrado em:** Super Mario Bros. Wonder: todo arquivo do RomFS dele é comprimido com zstd, 13.744 deixados de fora em ambas as versões; a primeira build com imagem logo depois da extração de pasta.

## Conteúdo de add-on

### DLC em Documents é ignorado ou DLC removido continua instalado

- **Sintoma:** o DLC de um jogo só funciona quando empacotado dentro do IPA, embora o RomFS base possa ser implantado separadamente. Depois de enviar um conjunto menor de DLC, índices removidos podem continuar reportados como próprios e montados.
- **Causa:** o launcher do iOS originalmente conferia só `<App>/aoc`. Apenas acrescentar a descoberta de `Documents/aoc` não basta: o `devicectl device copy to` mescla diretórios por padrão, retendo índices removidos, e pular uma build sem DLC deixa todo o conjunto anterior para trás. O host conta e monta as entradas numéricas sob `DM_AOC_DIR`, então aquelas sobras continuam ativas.
- **Correção:** o `aoc_locate` em `dm/ios/Sources/main.m` preserva um `DM_AOC_DIR` explícito do ambiente de lançamento ou do `env.txt`; senão ele seleciona o primeiro diretório em `Documents/aoc`, depois `<App>/aoc`, e registra `boot: DLC from <path>`. `Documents/aoc` é excluído dos backups. Dado `resources.env`, o `scripts/push_romfs.sh` transfere o diretório `DM_RESOURCE_AOC` completo com `--remove-existing-content true`, substituindo arquivos `<index>.img` antigos e árvores `<index>/` legadas. Um valor vazio ou omitido manda um diretório vazio, limpando o conteúdo anterior e selecionando explicitamente nenhum DLC externo em vez de recorrer ao conteúdo empacotado. Um caminho não vazio que está indisponível para antes de qualquer transferência. Um push direto de imagem de RomFS não tem metadados de DLC e deixa o DLC inalterado. As transferências não são atômicas: reexecute um push que falhou antes de lançar o jogo. Uso: [Reinstalações rápidas](../development.md#quick-reinstalls).
- **Encontrado em:** fixtures sintéticas de inicialização e de transferência ao revisar o [PR #486](https://github.com/seedds/nxnative/pull/486), parte da [issue #388](https://github.com/seedds/nxnative/issues/388). A fixture de Foundation roda o localizador real do iOS; a fixture do ajudante de push modela o comportamento de mesclagem e substituição documentado do devicectl, incluindo conjuntos de DLC menores e vazios e falha de transferência. Vale para todo jogo; nenhuma validação de jogabilidade em dispositivo foi feita.

## Metadados do launcher

### As configurações padrão de um front end de Mac mudam os caminhos de execução do Metal

- **Sintoma:** iniciar um app de Mac por um front end com configurações inalteradas habilita a thread de encode, e pode desabilitar os pipelines Metal 4 e o archive de pipelines; iniciar o mesmo app pelo Finder mantém os padrões do host.
- **Causa:** o `launcher.json` de Mac reusava os padrões de iOS do `settings.tsv`. O `rec_on` em `nvn_rec.h` tem padrão desligado no Mac e ligado no iOS; o `pso4_on` em `nvn_mtl.m` tem padrão ligado no Mac e segue o profile no iOS. Os padrões exportados em vez disso habilitavam a thread de encode em toda parte e seguiam o profile para o Metal 4 em toda parte. Um front end aplicando aqueles valores mudava o comportamento do host de Mac sem override do usuário.
- **Correção:** o padrão de uma configuração pode ser `<ios>|<mac>`, selecionado antes de resolver uma macro de profile ou uma variável de build. O Metal 4 usa `DM_GAME_PSO_MTL4|1`, a thread de encode `1|0`. O gerador valida a plataforma e o par. Os testes cobrem um profile com o Metal 4 ligado e um com ele desligado, e ambas as plataformas; o host e a chain de shaders ficam inalterados.
- **Encontrado em:** geração de metadados sintética para Super Mario Bros. Wonder ao revisar o [PR #352](https://github.com/seedds/nxnative/pull/352); conferido contra os padrões nativos, sem uma sessão de jogabilidade.

### A janela de configurações do Mac fica na tela depois de Play

- **Sintoma:** num app de Mac, a janela de configurações fica na tela depois de **Play**, sem responder (um cursor girando sobre ela), até o jogo terminar.
- **Causa:** a janela roda no processo do launcher (`dm/mac/Launcher.swift`). O `finish` mandou a janela sair e parou o `NSApp.run`; então o `launcher.c` iniciou o host e bloqueou no `waitpid`, então a thread principal nunca rodou outra passada do run-loop. A saída de uma janela é confirmada só no fim de uma passada dessas, e o fade-out padrão dela corre sobre várias passadas, então a janela nunca saiu da tela. Com o run-loop mantido rodando, a mesma saída teve efeito de uma vez.
- **Correção:** o `finish` define o `animationBehavior` da janela como `.none` antes de mandar a janela sair, e o `dm_mac_launcher` chama `CATransaction.flush()` depois que o `run()` retorna, antes de devolver ao `launcher.c`. Nenhum dos dois sozinho bastava. Checagem: uma cópia da janela com um Play cronometrado e uma sonda `CGWindowListCopyWindowInfo` enquanto a thread depois bloqueia; a janela ainda estava listada 2 e 4 s depois do Play antes da correção, e sumiu 3 vezes em 3 depois dela. `test_launcher_storage.py` e `test_nsp_mac_app.py` passam.
- **Encontrado em:** o app de Mac de Breath of the Wild; vale para todo app de Mac.

## Drives externos

### Uma pasta de jogo num drive exFAT lê um update como dois, ou falha ao remover uma pasta

- **Sintoma:** com a pasta do NSP num drive exFAT ou FAT, a build deixa de fora um update cujo nome não tem a tag `[v…]` (a pasta parece ter dois), ou um estágio para com `FileNotFoundError` num caminho `._<name>` dentro de `<id>_build/` e a execução seguinte falha na pasta meio-apagada.
- **Causa:** esses sistemas de arquivos não têm atributos estendidos, então o macOS guarda os atributos de um arquivo (o flag de quarentena de um download) num arquivo AppleDouble `._<name>` ao lado dele, e o apaga junto com o arquivo. O `scan_nsps` tomou `._Update [<title ID>800].nsp`, 4 KB de metadados, por um update: o nome dele carrega o title ID. Apagar `x` leva `._x` junto, então o unlink posterior do `shutil.rmtree` do `._x` listado o achou ido; antes do Python 3.13 aquele erro encerrava a remoção.
- **Correção:** o `scan_nsps` de `scripts/build_ipa_from_nsp.py` pega um arquivo só quando o cabeçalho dele é um que o nx_extract abre (`is_package`: `PFS0` em 0, ou o `HEAD` de um XCI em 0x100), e diz quais arquivos ele pula. A tag do nome sozinha não conta mais, então a mesma checagem também rejeita qualquer outro arquivo com tag que não é um pacote. Nomes que começam com `._` são pulados sem uma linha. O `rmtree` do script deixa passar ENOENT do `shutil.rmtree` (a entrada se foi, que é o objetivo) e lança todo outro erro. O `dm/tools/tests/test_nsp_external_drive.py` e o `test_nsp_scan.py` cobrem ambos sem arquivos de jogo.
- **Encontrado em:** os usuários do fork NX2Apple, que guardam jogos em drives externos ([PR #476](https://github.com/seedds/nxnative/pull/476), parte da [issue #388](https://github.com/seedds/nxnative/issues/388)); reproduzido numa imagem de disco exFAT feita com `hdiutil create -fs ExFAT`. Vale para todo jogo.

### O guard c1 para num arquivo AppleDouble depois da build de shaders

- **Sintoma:** com a pasta de build num drive exFAT ou FAT, o passo de shaders compila toda biblioteca e depois para no `c1_guard.py` com `UnicodeDecodeError: 'utf-8' codec can't decode byte …` (dmsh_build.py: `[RED] c1_guard.py failed`), lendo um `._<key>_b.metal`.
- **Causa:** os mesmos arquivos AppleDouble de cima, ao lado das saídas da build de shaders. O `c1_guard.py` tomou todo nome terminado em `.metal` pelo MSL de um shader e leu o arquivo binário `._` como texto. O `cb_extent.py` (todo `_b.json`) o pulou só porque ignora o que não consegue analisar, e o `dmsh_mtlcache.py` (todo `_b.metal`) tomou `._<key>_b` por um shader, não achou reflection legível para ele e então preencheu o cache Metal a partir de nenhuma das bibliotecas daquela pasta.
- **Correção:** os três pegam só os nomes que a build de shaders grava, `<16 hex key>_b….metal` / `.json` como o `dmsh_build.py` (`OUT_KEY`) e o `regress.py` já faziam: os `outputs` do `c1_guard.py` (que o `cb_extent.py` também usa) e o `OUTPUT` do `dmsh_mtlcache.py`. Nenhum deles faz parte da versão da chain. O `dm/tools/tests/test_nsp_chain.py` roda as duas ferramentas de tabela numa pasta com arquivos `._`; o `c1_guard.py` antigo para nele. Nos 751 shaders do 13 Sentinels ambas as tabelas ficam inalteradas.
- **Encontrado em:** uma build de shaders de iOS de um usuário num drive externo ([PR #555](https://github.com/seedds/nxnative/pull/555)). Vale para todo jogo NVN.

## Entradas comprimidas

### A descompressão de NSZ recusa `--keys`

- **Sintoma:** o `decompress NSZ` para de imediato com `nsz: error: unrecognized arguments: --keys …`.
- **Causa:** o `nsz` 4.6.1 não tem argumento `--keys`. Ele carrega `keys.txt` ao lado de `sys.argv[0]`, ou recorre a `~/.switch/prod.keys`, ao importar os módulos dele, antes de analisar argumentos ([carregador de chaves do 4.6.1](https://github.com/nicoboss/nsz/blob/4.6.1/nsz/nut/Keys.py)). A versão 5.0 suporta `--keys` ([analisador de argumentos](https://github.com/nicoboss/nsz/blob/5.0.0/nsz/ParseArguments.py)); colocar o `keys.txt` no lugar também suporta o 4.6.1.
- **Correção:** o `decompress_nsz` de `scripts/build_ipa_from_nsp.py` prefere o módulo do Python atual: ele vincula o arquivo selecionado por `-k` como `keys.txt` na pasta temporária da conversão e roda `nsz -D` lá, com `sys.argv[0]` definido como `nsz` antes do import. Sem o módulo, o `nsz_command` sonda `nsz` e `nsz-cli-macos-arm64` no PATH da build e passa `--keys` ao primeiro cuja ajuda bem-sucedida lista aquela opção. Um candidato não suportado ou que falha não esconde o próximo; quando nenhum funciona, o erro lista os motivos e as opções de instalação. Os caminhos do executável, da entrada e da saída são absolutos porque a conversão muda de diretórios. A pasta temporária e o link são removidos no sucesso ou na falha; as chaves padrão do usuário ficam intocadas.
- **Encontrado em:** Super Mario Odyssey, convertendo o NSZ v0 dele. Vale para entradas NSZ e XCZ de todo jogo. Testes sintéticos durante o [PR #327](https://github.com/seedds/nxnative/pull/327) também reproduzem um script de console mais antigo escondendo o binário da release, uma sondagem de ajuda que falhou contendo `--keys`, e um executável de PATH relativo falhando depois da mudança de diretório; nenhum arquivo de jogo é necessário para esses casos.

### Segmentos de NSO comprimidos com ZBIC

- **Sintoma:** o script do NSP ou qualquer ferramenta de módulo para no `main`: `compressed with zstd (NSO flag bit 7), which this loader does not decode yet`; com o decodificador mas sem o pacote dele, `ZBIC (zstd) segments need the zbic package (python3 -m pip install zbic)`.
- **Causa:** a partir do sistema 22.0.0, um NSO pode guardar os segmentos dele como **ZBIC**, NSO flag bit 7 para o módulo inteiro (os bits de compressão e de check-hash por segmento mantêm o significado). O ZBIC é a variante de zstd da Nintendo, não um contêiner em volta de frames padrão: os frames dele começam com o magic `ZBIC` e as tabelas FSE dele são gravadas com codificação interpolativa binária, então nem o `compression.zstd` nem o comando `zstd` conseguem lê-los.
- **Correção:** o `dm/tools/nso.py` decodifica esses segmentos com o pacote [`zbic`](https://pypi.org/project/zbic/) (do Kinnay, zstd com as mudanças de ZBIC do Atmosphère), importado só para um módulo com flag bit 7, então um título LZ4 não precisa de nada novo; todo segmento ainda é contido ao tamanho e SHA-256 do cabeçalho. O zstd não tem limite de razão fixo, então um segmento ZBIC é contido só ao tamanho próprio, onde um LZ4 também é contido a 255 bytes por byte armazenado. Instale-o com as outras ferramentas (README, passo 1).
- **Checagem:** o `main` do Well Dweller decodifica para 85.370.056 bytes com segmentos `0x39680d0 / 0x9f7e74 / 0x9b1930`, todo SHA-256 batendo; o `dm/tools/tests/test_nso.py` confere que um módulo com flag bit 7 cujos segmentos não são ZBIC é um Error nomeando ZBIC.
- **Encontrado em:** Well Dweller (SDK 22.2.0).

## Identificação de pacotes

### Um NSP sem ticket ou sem title ID no nome para com "no NSP with a readable title ID"

- **Sintoma:** `[RED] no NSP with a readable title ID in <folder>`, embora as chaves abram o pacote (a checagem de chaves do launcher passa). Renomear o arquivo para `Game [0100XXXXXXXXXXXX].nsp` faz a build continuar.
- **Causa:** o `title_of` pegava o title ID só do nome do arquivo do ticket (`<rights ID>.tik`) ou de uma tag `[title ID]` no nome do arquivo do pacote. Muitos NSPs não carregam ticket (dumps de standard-crypto, repacks), e o nome de arquivo de um download muitas vezes não tem tag.
- **Correção:** sem nenhum dos dois, o `title_of` pergunta ao pacote: o `nx_extract <prod.keys> --title <package>` o abre, decifra o cabeçalho de cada meta NCA com o `header_key` das chaves e imprime o title ID mais baixo (o do jogo base antes do update ou de um DLC). Funciona para NSP, NSZ (o meta NCA não é comprimido), XCI e XCZ, e roda só quando o ticket e a tag estão ambos ausentes, então os casos comuns ficam numa leitura da tabela de nomes de arquivo. O `nx_extract` é compilado para uma pasta temporária para isso, já que a pasta de build é nomeada pelo title ID. Os valores das chaves nunca são impressos.
- **Encontrado em:** NX2Apple, [LNPANDY/NX2Apple#177](https://github.com/LNPANDY/NX2Apple/issues/177) (Tears of the Kingdom, cujo NSP base não tem ticket). Vale para todo jogo.

### Um NSP mesclado (jogo base, update e DLC num arquivo só) empacota como um título

- **Sintoma:** uma pasta de jogo com um pacote mesclado (`[Base + Update + DLC].nsp`, ou um dump de cartucho 1G+1U sem um NSP de update ao lado) para com `no base game NSP found`, ou empacota o jogo base sozinho (v0) sem o update e o DLC; quando o build próprio do jogo base não pode ser empacotado (o `main` do Mario Kart 8 Deluxe 1.0.0 é de 32 bits), a build para aí.
- **Causa:** o `scan_nsps` dava a cada arquivo um title ID: o do primeiro ticket, senão a tag do nome. Um pacote mesclado guarda um ticket por título em qualquer ordem, então ele contava como o jogo base ou como o update, nunca como ambos, e o DLC dele nunca era visto. O `nx_extract` então lia o update só de um NSP de update separado.
- **Correção:** um pacote cuja tabela de arquivos (o PFS0 de um NSP, a partição secure HFS0 de um XCI) guarda mais de um `*.cnmt.nca` é perguntado pelos content metas dele, `nx_extract <prod.keys> --contents <package>` (uma linha `content <type> <title ID> <version>` cada), e conta como cada Application, Patch e AddOnContent que ele lista, com as versões dos metas. O arquivo único é então dado ao `nx_extract` como tanto o jogo base quanto o update: o `OpenNsp` guarda os NCAs que o content meta de Application lista para o base e os do content meta de Patch para o update, ambos da aplicação sendo empacotada (`--app`), e `--aoc <package> <out> <DLC title ID>` pega o NCA de dados de um DLC pelo title ID dele. A estimativa de extração, o total do progresso e a conversão de NSZ contam o arquivo uma vez. Quando os content metas não podem ser lidos, uma linha `[RED]` diz isso e o pacote conta pelo ticket como antes. Um NSP de DLC que empacota vários DLC é lido do mesmo jeito.
- **Encontrado em:** Mario Kart 8 Deluxe (0100152000022000, sem profile aqui) de um único NSP mesclado, no NX2Apple ([PR #842](https://github.com/seedds/nxnative/pull/842), [LNPANDY/NX2Apple#376](https://github.com/LNPANDY/NX2Apple/issues/376)). Conferido com o NSP de update e o NSP base do Balatro mesclados num único PFS0: ele varre como base v0 e update v851968, e o `nx_extract` dado como base e update escreve os mesmos ExeFS, dados de controle e manifesto de RomFS que os dois NSPs separados. Vale para todo jogo.

## Dumps de cartucho

### Um dump de cartucho com o update nele extrai o update como o jogo base

- **Sintoma:** a extração de um jogo cuja base é um XCI que também carrega o update (um dump "1G+1U") para com `[RED] nx_extract exit code -6`. O `extract_v<version>.log` lista os build IDs do update mesmo para o jogo base sozinho, depois termina numa exceção não tratada do RomFS (`ResultFsNonRealDataVerificationFailed (2002-4604): Hash error!` de `RomFsFileSystem..ctor`, ou `ArgumentException` / `InvalidOperationException` das camadas de patch).
- **Causa:** a partição secure do XCI guarda os NCAs do update ao lado dos do jogo base, e o Program NCA do update também tem o title ID do programa. O `nx_extract` tomava o primeiro Program NCA do title ID mais baixo como o base, que é o do update quando o dump o lista primeiro. A seção de dados dele é um patch (BKTR) sobre o RomFS base, então não pode ser lida sozinha nem sob outro patch. O ExeFS ainda abre, com os build IDs do update, porque a seção de código de um update é completa. O Control NCA (versão de exibição, ícone) também era qual dos dois viesse por último.
- **Correção:** o `OpenNsp` de `dm/tools/nx_extract/Program.cs` lê os content metas do pacote base (os `*.cnmt` nos Meta NCAs dele) e guarda só os NCAs que o content meta de Application dele lista, e imprime quantos deixou de fora. Quando nenhum deles é um Program NCA (arquivos NCA renomeados, então os nomes não são content IDs), ele imprime uma linha `[RED]` e lê todo NCA como antes. Um NSP ou um XCI só de base guarda todo NCA menos o meta NCA, então extrai como antes (os NSPs do Balatro e o XCI do Monster Hunter Rise dão manifestos idênticos). O update no cartucho também é empacotado desde que [um pacote mesclado conta como cada título que guarda](#um-nsp-mesclado-jogo-base-update-e-dlc-num-arquivo-so-empacota-como-um-titulo).
- **Encontrado em:** The Legend of Zelda: Tears of the Kingdom, um XCI 1G+1U (base v0 com update 1.4.3, cujo Program NCA de 524 MB é listado antes do de 17,1 GB do base) ao lado do NSP de update 1.4.3 ([PR #311](https://github.com/seedds/nxnative/pull/311)). Reproduzido com um pacote do NSP de update do Balatro seguido do NSP base dele: o base sozinho e o base com o update agora dão os mesmos manifestos e dados de controle que os NSPs separados. Vale para qualquer XCI de jogo que carregue o update.

### Um dump de cartucho que guarda dois jogos empacota só o primeiro

- **Sintoma:** um XCI com duas aplicações (Super Mario Galaxy + Super Mario Galaxy 2 num único dump de cartucho) sempre empacota o primeiro jogo; o `build_ipa_from_nsp.py` nunca chega ao segundo.
- **Causa:** a varredura tomava um title ID por arquivo (as tags do nome marcam ambos os jogos, e a primeira tag vencia), e o `nx_extract` guardava os NCAs de todo content meta de Application e tomava o Program NCA do title ID mais baixo. Nada podia nomear a outra aplicação.
- **Correção:** os content metas do XCI fazem com que ele [conte como cada título que guarda](#um-nsp-mesclado-jogo-base-update-e-dlc-num-arquivo-so-empacota-como-um-titulo), então a varredura acha dois jogos e para com `more than one game in the folder`, nomeando ambos. O `--title-id <title ID>` (`TITLE_ID` no Spyder) escolhe o jogo a empacotar entre eles; o script passa o title ID dele a toda extração de base (`nx_extract … --app <title ID>`), e o `OpenNsp` guarda só os NCAs dos content metas de Application e Patch daquele título (um `--app` que o pacote não tem content meta dele para com os que ele tem). Cada jogo ganha a própria pasta `<title ID>_build/` e o próprio app.
- **Encontrado em:** Super Mario Galaxy 2, no mesmo XCI do Super Mario Galaxy ([PR #701](https://github.com/seedds/nxnative/pull/701), que empacotou ambos do XCI com uma forma anterior da opção). Esta forma é conferida com a tabela de arquivos de um XCI de teste e com os pacotes do Balatro (um `--app` de um título que o pacote não guarda para, nomeando o que ele tem); nenhum XCI de dois jogos está à mão.

## Pacotes danificados

### A extração de um NSP danificado termina em "The LinkedList is empty"

- **Sintoma:** o `nx_extract` para com código de saída 134 e `Unhandled exception. System.InvalidOperationException: The LinkedList is empty.` de `LibHac.Tools.FsSystem.CachedStorage.GetBlock`, sem lista `[RED] hash check failed`, com ou sem `--allow-damaged`.
- **Causa:** um NSP danificado com mais de uns poucos arquivos danificados esgotava o cache de hash do LibHac 0.19. O `CachedStorage.GetBlock` tira um bloco da lista antes de ler nele e não o devolve quando a leitura falha, então os 4 blocos de um sistema de arquivos duram 4 leituras que falham e a próxima leitura que erra o cache lança. Aquela exceção não é um erro de hash, então o `nx_extract` não a capturava. Uma cópia de SteamWorld Dig com 2 bytes virados listava os 2 arquivos; com 40 derrubava.
- **Correção:** cada erro de hash ganha um novo sistema de arquivos checador (`Failed` em `dm/tools/nx_extract/Program.cs`, nos caminhos de imagem, pasta e manifesto), então um NSP danificado lista cada arquivo danificado e para com código de saída 3, ou continua com `--allow-damaged`. A mesma cópia com 40 bytes virados lista os 36 arquivos. O `test_every_damaged_file_is_listed_past_the_hash_cache` em `dm/tools/tests/test_romfs_read.py` põe um RomFS real atrás de um `CachedStorage` real nos três caminhos, sem NSP nem chaves.
- **Encontrado em:** Breath of the Wild ([issue #810](https://github.com/seedds/nxnative/issues/810), cujo relator diagnosticou os blocos de cache perdidos e carregava um patch local que reabre o sistema de arquivos). Vale para qualquer jogo.

### Um crash de um arquivo de NSP danificado parece um bug do host

- **Sintoma:** uma build empacotada com `--allow-damaged` derruba ou desenha errado em código do jogo, do mesmo jeito a cada execução, num lugar sem relação com o último trabalho do host. O log não deu sinal de dano; a lista do log de build (`logs/extract_<version>.log`) é o único registro, e não faz parte do log de execução de um relatório de bug.
- **Causa:** o `--allow-damaged` escreve os arquivos que falharam na checagem de hash do NCA como foram lidos, e nada dizia ao host em execução. Um byte errado num pack comprimido decodifica para dados errados longe de onde o jogo depois falha. Um bloco de hash também abrange arquivos pequenos vizinhos, então os bytes de um arquivo listado podem ainda estar certos.
- **Correção:** o último byte da entrada num índice `DMROMFS1` ([formato](../../dm/tools/romfs_image.py)) é 1 num arquivo que falhou na checagem (`img_ent.flags`, `romfs_image.h`; o `nx_extract` o define, e todo leitor recusa outro valor, ou uma flag num diretório). A marca fica com a imagem num IPA, num app de Mac ou num `romfs.img` copiado à mão. O host registra `[RED] fs RomFS image <path>: damaged files <N>: ...` na montagem e `[RED] fs rom:/<file> failed the NCA's hash check ...` na primeira abertura de cada arquivo danificado. Uma imagem limpa é byte-idêntica a uma de antes desta marca (conferido em SteamWorld Dig), então a identidade dela não muda. Não marcados: uma imagem extraída antes desta mudança, e a extração de pasta, que não tem índice (o script do NSP grava imagens). Procure `hash check` no log de um crash antes de procurar uma causa no host.
- **Encontrado em:** Breath of the Wild ([issue #810](https://github.com/seedds/nxnative/issues/810)). O `dm/host/tests/t_fs.c` confere a contagem, o único relatório na primeira abertura e as flags recusadas; um boot de SteamWorld Dig numa imagem deliberadamente danificada registrou a contagem e os arquivos que abriu.

## Jogos base esparsos

### A busca de build ID do survey para no jogo base sozinho com um erro de hash

- **Sintoma:** para um jogo sem profile, o script do NSP para em `build ID lookup · main of the base game` com `[RED] nx_extract exit code -6`; o `<title ID>_survey/logs/exefs.log` termina em `ResultFsNonRealDataVerificationFailed (2002-4604): Hash error!` de `PartitionFileSystemMetaCore.QueryMetaDataSize` sob `Nca.OpenFileSystem`, embora todo NCA em ambos os NSPs bata com o content ID dele (o SHA-256 que o nomeia) e o jogo base com o update extraia limpo.
- **Causa:** o Program NCA do jogo base é esparso: as seções de código e dados carregam uma camada esparsa e deixam de fora dados que o update fornece, então o base é menor que o update (1,6 GB contra 2,9 GB). O Horizon monta um NCA desses só pelo patch; lido sozinho, as faixas deixadas de fora falham na checagem de hash desde o primeiro bloco do ExeFS. A busca (`same_build`) tenta o build ID do main do update mais novo primeiro, depois o do jogo base sozinho, e o `run` parava a build na falha da segunda tentativa.
- **Correção:** o `dm/tools/nx_extract/Program.cs` para com código de saída 4 e `[RED] the base game's program is sparse: it can be read only with its update NSP` quando recebe um base esparso sem um update (qualquer seção habilitada do Program NCA com uma camada esparsa). O `run` de `scripts/build_ipa_from_nsp.py` aceita os códigos de saída que um chamador aceita (`ok`), e o `same_build` aceita 4: o jogo base sozinho então não tem main próprio e a busca continua. O jogo base com o update lê como antes (o LibHac sobrepõe o update ao base esparso; os 4,2 GB inteiros de RomFS mesclado do jogo abaixo leem com toda checagem de hash ligada).
- **Encontrado em:** Minecraft Dungeons II (`0100A7C01B792000`, sem profile ainda), base v0 (SDK 22.2.0) com update v131072 (1.1.3.0). Vale para qualquer jogo cujo Program NCA base é esparso.

## Empacotamento no celular

### Prepare não é oferecido para um jogo cujo build suportado é seu jogo base

- **Sintoma:** no Android, o **Add game** numa pasta de dump com `base/exefs` e `base/romfs` mas sem `updates/` (ou um `.nup` com só um pacote base) não oferece Prepare: ele pede "Pick the pack folder", o card do jogo não tem Prepare, e o ⋯ não tem Prepare again. Só um pack feito no Mac funciona.
- **Causa:** o teste do app de se uma pasta escolhida é um dump completo (`Ondevice.isDump`) pedia uma pasta `updates/` (e, para um `.nup`, um pacote de update). O `DumpCheck`, o `pack_dump.py` e os passos do job já tomavam a versão 0 (o jogo base em si) como o build a preparar; só esse primeiro teste a recusava. Um jogo cujo build suportado vem no Application content base não tem update para despejar.
- **Correção:** o `Pack.isDump` (Java puro, rodado pelo `NupJvmTest`): um dump é `base/exefs/main.npdm` e ou uma pasta `updates/` ou o `exefs/main` do próprio jogo base com um `romfs/` não vazio; um `.nup` é um pacote base com um pacote de update ou com um ExeFS e um RomFS próprios. A pasta de uma só versão ainda não é um dump. O `DumpCheck` nomeia a versão 0 como "the base game" nas mensagens (`Profile.supported`, `Profile.versionName`), e os diálogos do Prepare dão o tempo pela contagem de shaders do jogo (`ShaderLibs.jobMinutesText`) em vez de um número fixo.
- **Encontrado em:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#prepare-no-celular-180) 1.8.0 (versão 0). Vale para todo jogo cujo build do profile é o base.

### "Pack from other tools" num pack que o próprio app fez

- **Sintoma:** a Home do NativeAYN mostra o chip "Pack from other tools" (a nota no card de que o código é de outras ferramentas) num pack que o próprio Prepare dele fez, embora nenhum arquivo do reescritor tenha mudado desde; ⋯ › **Prepare again** reescreve o código para limpá-lo.
- **Causa:** a rewrite key (`<module>.android.key`, o `rewrite_key` do `pack_android.py`, o `RewriteKey` do launcher) hasheava o `game.tsv` inteiro do profile. O reescritor lê só as linhas `build` dele (o `patch_nso.py`, para os match cuts de um build sem cuts registrados; nenhum outro arquivo `REWRITER` lê o profile); as outras linhas são do host (timing de GPU, tamanho de janela, escala gráfica). Qualquer linha dessas acrescentada a um profile tornava obsoleto todo pack existente daquele jogo: as linhas `gpu_timestamps` / `android_window` / `romfs_check` do Donkey Kong Bananza, as linhas `graphics_scale` do Mario Kart World.
- **Correção:** a chave hasheia só as linhas de build (`build_rows`, normalizadas: cada célula despojada, outras linhas deixadas de fora; sob o nome `game.tsv build rows`). Uma chave da fórmula anterior ainda conta, com o `game.tsv` do APK ou com a cópia do próprio pack (`<pack>/game.tsv`, que o `pack_android.py` escreve depois da rewrite) quando as linhas de build dessa cópia são as do profile: a chave prova que a cópia é o arquivo com que foi feita. A mesma regra no `pack_android.py` (`rewrite_keys`: o módulo é mantido) e no launcher (`RewriteKey.keys`, `PackCheck.code`). O empacotador escreve uma chave dessas como a atual antes de substituir a cópia do pack (`upgrade_keys`; o passo de só-shaders do pack no celular também a substitui), então o pack não a perde. Um pack sem cópia é julgado como antes. Testes: `dm/tools/tests/test_android_rewritekey.py` (Python e `RewriteKeyJvmTest`).
- **Encontrado em:** [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#encontrado-neste-jogo) (os packs do celular do update 458752, chaves do reescritor em ffe72d71 e b4269ab1) e [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#encontrado-neste-jogo) 1.8.0 (todos os quatro módulos); cada um agora conta como atual, conferido com a chave em Python e a em Java nos packs puxados do celular. Vale para todo jogo.

### O passo de shaders do celular falha num shader que também não compila no Mac

- **Sintoma:** o passo de shaders do Prepare para com `[RED] 1 of 11604 shaders did not build: no library written (DMSH_VK_REQUIRE_ALL)` depois de uma linha `[RED] translation failed: 1 shaders, e.g. <key>`; o Retry traduz aquele shader de novo e para do mesmo jeito. Uma build de Mac da mesma versão grava a biblioteca e registra `[RED] delta check: <key>: not in the library (translation failed: …), the manifest has -`.
- **Causa:** o `DMSH_VK_REQUIRE_ALL=1` (o switch do celular: uma biblioteca sem shaders nunca deve passar como terminada) pedia que todo shader do map do profile compilasse. Um shader que o tradutor ainda não consegue traduzir também falta na biblioteca do Mac, e o manifest de delta do profile (`vk_delta.tsv`, uma build de Mac completa daquela versão da biblioteca) o registra como `-`; a regra pedia ao celular mais do que o Mac produz. A checagem de delta comparava `-` com "sem entrada" como dois valores diferentes.
- **Correção:** a regra é "todo shader que a build do Mac desta versão guarda": o `vk_android_build.py` tira das falhas os shaders que o manifest do profile desta versão tem como `-` (`vk_android_delta.py not_built_there`) e os nomeia numa linha simples; qualquer outra falha ainda não escreve biblioteca. Sem um manifest desta versão (uma mudança de ferramentas antes de `--publish-delta`) todo shader tem que compilar, como antes. A checagem de delta toma um shader `-` que não está na biblioteca como o manifest o tem (`entry_as_manifest`). A biblioteca é byte-idêntica à de antes da mudança (linha `088af9aa5109` do `vk_android_same.tsv`).
- **Encontrado em:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#prepare-no-celular-180) 1.8.0: compute `078997bf631992c5` (instrução Ampere `0x481`, não implementada), 11.603 de 11.604 shaders por projeto.
