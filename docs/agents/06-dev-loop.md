# 06 — O loop do desenvolvedor: qual ferramenta quando, e antes de um pull request

Uma página para pessoas: as ferramentas que este repositório tem para compilar, executar, depurar, medir e checar uma mudança, quando usar cada uma, e o que um pull request precisa. Ela liga para onde cada ferramenta está descrita em vez de repetir. Arquivos de jogo, chaves, builds e execuções ficam fora do repositório ([docs/development.md](../development.md)).

## 1. Build e execução no Mac

| Etapa | Ferramenta | Detalhes |
|---|---|---|
| Pack de um jogo para o Mac | `scripts/build_ipa_from_nsp.py <NSP folder> -k <prod.keys> --platform mac` | Extração, rewriter, shader split e chain, o host do Mac; imprime o comando que roda o jogo. [Uma build só de Mac para desenvolvimento](../development.md#a-mac-only-build-for-development) |
| Um app clicável duas vezes | a mesma com `--platform mac-app` (acrescenta o archive offline de pipeline) | [Um app de Mac](../development.md#a-mac-app) |
| Uma build de iPhone | a mesma sem `--platform` (um IPA não assinado que o usuário sideloada) | [O script de pack em detalhe](../development.md#the-packing-script-in-detail) |
| Recompilar só o host | `make -C dm/host GAME=<id>` | [Compilar à mão (Mac)](../development.md#build-by-hand-mac) |
| Recompilar só os shaders | `DM_GAME=<id> dm/gfx/tools/dmsh_build.py` (depois de uma mudança na chain: primeiro `dmsh_chain.py --header`) | o procedimento da chain em [docs/development.md](../development.md); [04](04-graphics.md) |
| Rodar com input roteirizado | `DM_KEYS` (apertões de botão em segundos ou frames fixos), `DM_CTL` (apertões, screenshots e dumps durante a execução), `DM_REC` (registra o que o player faz como passos de `DM_KEYS`, para reproduzir o caminho de um bug report ou montar uma rota) | [05, Input roteirizado](05-debugging.md#input-roteirizado-e-escalonamento-de-threads) |

Comece execuções no Mac com o HUD de performance do Metal (`DM_METAL_HUD=1`). Um título novo começa pelo [checklist](README.md#checklist-para-um-novo-titulo) e [03](03-bringup.md).

## 2. Quando algo está errado

1. Procure no [índice de sintomas](symptoms.md) pela linha `[RED]`, pelo texto do abort ou pelo que você vê; ele leva à entrada de referência e aos jogos onde foi achada.
2. Crashes: o relatório `CRASH sig=…` do host, o crash report do macOS, scripts do lldb, Ghidra / objdump nos módulos reescritos: [05](05-debugging.md#lendo-um-crash-report).
3. Hangs e threads: `DM_WATCH=<s>` / `DM_WATCH_STALL=<s>` despejam todas as threads ([03, Lendo o log](03-bringup.md#lendo-o-log)); `DM_THR=1`, `DM_SVC=1`, `DM_FS=1` registram em log SVCs de thread, SVCs de memória e aberturas de arquivo; `sample` / `xctrace` nomeiam as threads convidadas durante um hitch ([05](05-debugging.md#input-roteirizado-e-escalonamento-de-threads)); `DM_HLECOUNT=<file>` conta cada função HLE e SVC que o jogo chamou.
4. Estado do convidado sem um depurador: `DM_PROBE` e suas variantes de watch e heap ([05](05-debugging.md#sondas-sem-depurador-dm_probe)).
5. Imagem errada: screenshots com `DM_NVN_SHOT`, `DM_NVN_PASSDUMP` (cada pass, seus attachments, bindings e estado de draw), `DM_NVN_TEXDUMP` / `DM_NVN_TEXSNAP` (render targets como PNG), `DM_NVN_CBDUMP` (uniform buffers, streams de vértices), `DM_NVN_HILITE` / `DM_NVN_DEPTHOVR` / `DM_NVN_SKIP_FS` (isolar um draw), `DM_NVN_KEYDUMP` e `DM_NVN_MAGSCAN` no celular: [04, Switches de diagnóstico](04-graphics.md#7-switches-de-diagnostico-host) e [05, Glitches de renderização intermitentes](05-debugging.md#glitches-de-renderizacao-intermitentes).
6. Frames lentos: as linhas `[longframe]` e o despejo de hitch (`DM_HITCH_DUMP`), esperas de compilação de pipeline ([05](05-debugging.md#esperas-de-compilacao-de-pipeline)), tempo de GPU por pass (`DM_NVN_GPUPROF`, fases A/B do `DM_AB`, `DM_GPU_CAPTURE` para o Xcode; leia com `dm/tools/gpuprof.py`): [05, Tempo de GPU no dispositivo](05-debugging.md#tempo-de-gpu-no-dispositivo). Tráfego de attachments: `dm/gfx/tools/tbdr_*.py` sobre um dump de pass.
7. Memória: a linha de memória do host, `footprint`, `vmmap`, `DM_NVN_ALLOCPROF=1`: [05, Crescimento de memória](05-debugging.md#crescimento-de-memoria).
8. Shaders: `dm/gfx/tools/shader_regressions.py` (shaders que compilaram na chain anterior e falham agora), `DM_NVN_SHDUMP` (programas ausentes do mapa), a checagem de link offline ([05](05-debugging.md#checagem-de-link-de-pipelines-offline)).
9. No iPhone: switches em `Documents/env.txt`, resultados em `Documents/log.txt` ([05, Diagnóstico no dispositivo](05-debugging.md#diagnosticas-no-dispositivo-ios)).
10. Atualizações de jogo e endereços fixos: `dm/tools/nso_fnmap.py`, `nso_syms.py`, `insn_census.py`, `sdis.py`, `nso2elf.py` ([Ferramentas](../development.md#tools-dmtools)).

## 3. Medindo

`scripts/bench.py <id>_build --route <name>` roda uma rota do `bench.tsv` do profile a partir de um save fixo e dá percentis de tempo de frame, tempo de GPU e screenshots; variantes (`--variant`) comparam dois hosts, bibliotecas de shaders ou conjuntos de switches numa só invocação, que é a única comparação que ela suporta ([Um benchmark no Mac](../development.md#a-benchmark-on-the-mac)). Potência e energia por frame: [Potência](../development.md#power). Passe `--lock <file>` quando outras pessoas medirem no mesmo Mac: a lock é segurada só enquanto um jogo roda, e builds pesadas devem esperá-la.

## 4. Checando uma mudança em todos os jogos: `scripts/regress.py`

Uma só chain e um só host servem a todos os profiles, e cada contribuidor é dono de só alguns jogos (GitHub issue #272). O `scripts/regress.py` compara uma revisão de baseline (por padrão a merge base com `main`) com uma candidata (por padrão este checkout, incluindo arquivos não commitados) em todos os jogos para os quais o Mac tem uma build `--platform mac`. Sua contagem de shaders usa a regra do `shader_regressions.py`, que o script do NSP aplica a um jogo que você recompila; o harness acrescenta os outros jogos, o MSL, a interface de pipeline e uma execução. Descrição completa: [O harness de regressão](../development.md#the-regression-harness).

| Comando | O que roda | Custo |
|---|---|---|
| `regress.py chain` | Estático: a build de shaders de cada revisão, comparada shader por shader (compilada ou falhou, hashes de MSL / reflection / variante), e a interface de vértice / pixel das bases do archive de pipeline (issue #283) | nada quando a chain não mudou; uma chain mudada traduz todos os shaders de novo (14 min para os 19.592 de Breath of the Wild num M2 Max) |
| `regress.py check --quick` | O acima mais um boot curto por jogo: os segundos `quick` da rota, sem prebuild de pipeline | cerca de um minuto por jogo e execução |
| `regress.py check` | A rota inteira com o prebuild de pipeline primeiro (`DM_PSO_PREBUILD=tool`) sob um watchdog | Breath of the Wild uns 5 min, Tears of the Kingdom uns 7 |
| `regress.py replay` | A captura de frame atual de cada jogo reproduzida pelo `nvn_replay` das duas revisões, com suas próprias bibliotecas de shaders, comparada com o frame ao vivo até o dobro do ruído da captura; `regress.py capture --rev main` registra a captura (o frame `capture` da rota) e mede o ruído dela ([Captura e replay de frame](../development.md#frame-capture-and-replay)) | segundos por jogo quando os replayers e as chains já estão compilados; confere só a camada de replay (`nvn_mtl.m` e abaixo) |
| `regress.py baseline --rev main --runs 2` | Registra um baseline (um ausente é registrado pelo próprio `check`); duas execuções dão o ruído | como `check`, por execução |

As rotas ficam em `dm/games/<id>/smoke.tsv`; um jogo sem uma participa só das checagens de chain. Adicione uma quando você for dono de um jogo: um save fixo, os apertões que o carregam (escritos à mão, ou jogados uma vez com `DM_REC` e unidos numa linha), screenshots só enquanto o player fica parado (onde uma caminhada termina muda de execução para execução), e o frame que ela deve alcançar.

Adicione `--record` ao check nos seus jogos (`check --record`, ou `baseline --record`) e commite o `dm/games/<id>/validated.tsv` que ele escreve junto com o pull request: ele mostra em qual chain cada jogo esteve verde pela última vez (`regress.py list` imprime isso). Um registro exige `PASS` ou `CHANGED` e execuções de boot bem-sucedidas, mesmo quando o baseline tem a mesma falha de boot. Profiles de build derivados não validam profiles do repositório. O relatório é salvo antes de os metadados serem escritos. Sem `--record` o harness não muda nada em `dm/games`.

As execuções de smoke de NVN também comparam o modo de profundidade observado com o `depth_mode` do profile, mesmo sem um archive no modo quick, e detectam um archive empacotado rejeitado por divergência de stamp. Veja [divergências de profundidade entre archive e profile](../reference/shaders.md#offline-pipeline-archive-and-profile-depth-disagree). Observações de runtime ausentes continuam desconhecidas.

Lendo o relatório (`report.md` ao lado de `report.json` em `<root>/reports/`): uma linha por jogo, depois os detalhes. `PASS` e `CHANGED` (MSL ou números mudaram, nada piorou) saem com 0; `NEW-FAIL` (um shader, a checagem de interface, um crash, um hang ou o frame que funcionava no baseline falha) e `REGRESSION` (linhas `[RED]` novas, um screenshot, tempo de frame, memória ou tempo de prepare além das tolerâncias) saem com 1; `ERROR` (o harness não conseguiu checar um jogo) sai com 2. Falhas que o baseline também tem são listadas como conhecidas e não reprovam a checagem. MSL mudado é esperado depois de uma mudança na chain: diga no pull request por que mudou. Uma diferença de screenshot pode ser um conserto: olhe os screenshots da execução em `<NSP folder>/<id>-work/regress/runs/` antes de afirmar qualquer coisa. O relatório contém só números, hashes, chaves de shader e textos `[RED]` normalizados, então pode ser colado como está.

## 5. Quais jogos uma mudança pode alcançar: usage manifests e `regress.py impact`

O `regress.py` confere só os jogos que estão no seu Mac. Para os outros, cada profile pode carregar um usage manifest, `dm/games/<id>/usage.tsv`, escrito por alguém dono do jogo com `python3 scripts/regress.py usage --games <id> --write`: os recursos dos seus shaders traduzidos (estágios, tipos de binding, atomics de imagem e de buffer, transform feedback, saídas de layer e de inteiro, notas do tradutor, tipos de textura), e, de uma execução da sua rota de smoke, as funções NVN, as funções HLE e as SVCs que ele chamou, o seu caminho presente e as suas chaves de profile. Ele guarda só nomes e contagens.

`python3 scripts/regress.py impact <base>..<head>` (ou um único commit) mapeia uma mudança para esses nomes: as funções em torno das suas linhas alteradas, seguidas pelos chamadores no host até os entry points de NVN e as funções HLE que elas servem, e as regras de `dm/tools/impact_map.tsv` (um arquivo, ou funções nele, para linhas de manifest: `dmsh_atomic.py` para os recursos de atomic de imagem, as funções do passo de prepare de `nvn_mtl.m` para os jogos que o executam). Ele lista os jogos que usam o que a mudança toca, os alcançados só por uma regra ampla (todo jogo da API), e os profiles sem manifest como desconhecidos. Ele lê só o git e os manifests commitados, então não precisa de arquivos de jogo nem de uma raiz de harness: o relatório é impresso e escrito como `impact.md` e `impact.json` em `--out` ou, quando existir uma, em `<root>/reports/`. Rode-o antes de uma mudança na chain ou no host, e rode `regress.py check` nos jogos que ele nomeia e que você tem; para os outros, peça aos donos. Um arquivo alterado que nenhuma regra mapeia é listado: adicione uma regra para ele.

## 6. Integração contínua

O `.github/workflows/tests.yml` roda em todo pull request: os testes unitários do host e os alvos de ThreadSanitizer, o host e os testes de textura de CPU de novo sob ASan, UBSan e TSan (um ratchet sobre as descobertas listadas em `dm/sanitizers/`: `make -C dm/host/tests GAME=<id> asan tsan-threads` e `make -C dm/gfx/tex/tests asan` localmente), a cobertura de linhas desses testes e dos testes das ferramentas com a cobertura do diff do pull request no resumo do job (só relatório; localmente, `make coverage` nas duas pastas e `dm/tools/coverage_report.py`), os testes gráficos de CPU apenas, os testes das ferramentas Python (`dm/tools/tests`, `dm/ios/tests`, `dm/gfx/tests`) incluindo os testes de shaders sintéticos do tradutor, builds do host de Mac para um profile NVN, um Vulkan e um OpenGL, e a compilação da fonte iOS e o projeto de smoke ([Integração contínua](../development.md#continuous-integration)). O `.github/workflows/fuzz.yml` fuzza os parsers de arquivo toda noite a partir de seeds sintéticos; uma mudança num parser em `romfs.py`, `nacp.py`, `shader_split.py` ou `uepak.py` pode rodar seu harness localmente (`dm/tools/fuzz/fuzz_<parser>.py --time 300`). Os Macs do GitHub não têm Metal 4 nem arquivos de jogo, então isto continua local: `make -C dm/gfx/tests GAME=<id> run` (os testes gráficos de Metal), os testes do tradutor com `DMSH_TEST_METAL=1` / `DMSH_TEST_GPU=1`, `profile_guess.py --check`, e tudo o que o `regress.py` faz.

## 7. Antes de abrir um pull request

Pelo que a mudança toca (o maior que se aplica):

- **Só docs:** `python3 -m unittest dm/tools/tests/test_docs.py`; depois de uma mudança em `docs/reference`, `python3 dm/tools/docs_symptoms.py`.
- **Uma ferramenta ou script Python** (`scripts/`, as ferramentas sob `dm/`): o ratchet que o `lint-python.yml` roda, ruff e pyright sem descoberta nova: `<venv>/bin/python3 dm/tools/lint_python.py`, num venv com `.github/requirements/lint.txt` instalado, mantido no disco das pastas NSP, não na pasta home ([Integração contínua](../development.md#continuous-integration)). O Python do sistema não tem nenhuma das duas ferramentas, e a checagem ali para numa linha `[RED]`: isso não é um passe. Uma página gerada (`docs_*.py`) é comparada na CI num checkout limpo, então não deve ler arquivos não rastreados ou ignorados pelo git, como `dm/host/gen`.
- **O profile ou a nota de um jogo** (`dm/games/<id>/`): os testes das ferramentas Python; uma build completa de shaders daquele jogo depois de uma mudança nos seus inputs de shader; o jogo no Mac (ou no iPhone) ao longo da sua rota, com números do `scripts/bench.py` quando a mudança é sobre velocidade; a descoberta na nota do jogo ([docs/development.md](../development.md)).
- **O host, a chain ou as ferramentas** (`dm/host`, `dm/gfx`, `dm/tools`, `dm/gfx/tools`, `dm/ios`, `scripts`): tudo acima, `make -C dm/gfx/tests GAME=<id> run`, `dmsh_chain.py --header` depois de uma mudança na chain, `python3 scripts/regress.py impact main..HEAD` para ver quais jogos ela alcança, depois `python3 scripts/regress.py check --games <ids>` (`--quick` enquanto iterar, a execução completa antes do pull request), e o `report.md` dela colado no pull request com uma palavra sobre cada `CHANGED`, `NEW-FAIL` ou `REGRESSION`. Escolha os jogos, não todos os locais: os cinco que a mudança tem mais chance de alcançar ou quebrar (os que `impact` nomeia, depois jogos que cubram as APIs, engines e caminhos que ela toca). Passe de cinco só quando a mudança realmente precisar (uma mudança ampla de chain ou host que cinco jogos não cobrem), e menos quando seu alcance for estreito e claro (um conserto num caminho de um só jogo, uma ferramenta que só alguns jogos usam). Nomeie os jogos que o relatório cobre e por que os escolheu: os demais ficam não conferidos. Depois de uma mudança em C ou Objective-C em `dm/host` ou `dm/gfx`, `dm/tools/lint_c.py compdb` e `tidy` com o release do LLVM rodam o que o workflow `lint-c` roda: nenhuma descoberta nova (conserte-a, ou `// NOLINT(<check>)` com um motivo num falso positivo), e `tidy --update` depois de consertar uma ([Integração contínua](../development.md#continuous-integration)).
