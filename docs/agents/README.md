# Portando um título de Switch: guia para agentes

Estas páginas são para um agente incumbido de analisar um NSP de Switch e portá-lo com a abordagem de execução nativa deste repositório e do [d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile): o próprio código aarch64 do jogo roda nativamente no hardware Apple, um rewriter corrige apenas as instruções que o kernel da Apple não pode executar, o host substitui os serviços de sistema do Horizon, e o NVN é reimplementado sobre Metal.

Tudo aqui foi aprendido em Diablo II: Resurrected (SDK ~12, NVN 53, o alvo original do d2r-mobile) e Super Mario Bros. Wonder (SDK 16.2.0, NVN 55, neste repositório; seu update 1.2.1 usa SDK 16.2.12), e depois ampliado por Fire Emblem Engage (Unity, SDK 12.3.7), Metroid Dread (engine da MercurySteam, SDK 11.4.3), 13 Sentinels: Aegis Rim (engine da Vanillaware, SDK 11.4.3, os mesmos módulos `sdk` e movie do Dread), Super Mario 3D World + Bowser's Fury (engine sead / agl da Nintendo EPD, SDK 10.4.0, API NVN 53), The Legend of Zelda: Breath of the Wild (engine sead / ksys da EPD, SDK 20.5.22, realocações `DT_RELR`, update 1.9.0), The Legend of Zelda: Link's Awakening (engine da Grezzo sobre NintendoWare, SDK 8.2.0, origem da janela no canto inferior esquerdo), Hyrule Warriors: Age of Calamity (KTGL da Koei Tecmo, SDK 9.6.0, arquivos RDB, shaders como saídas GLSLC), Super Mario Galaxy (um jogo de Wii sobre a camada Hagi da NERD: código PowerPC recompilado, SDK 18.3.5, Vulkan com SPIR-V gerado em tempo de execução, 2.9 GB de bss), Ace Attorney Investigations Collection (Unity 2022.3 IL2CPP, SDK 17.5.3: a API de arquivos C# através da biblioteca C do SDK) e o bring-up de Octopath Traveler 0 (Unreal Engine 5, SDK 19.3.13: um pak criptografado com AES, shaders comprimidos com Oodle que o próprio código do jogo decodifica no Mac, seu alocador substituído pelo do host). Onde os títulos diferiram, cada diferença é indicada; o próximo título vai diferir de novo, então trate todo número abaixo como "meça, não presuma".

## Regras fundamentais

- **Traga seus próprios arquivos.** Chaves, NSPs e qualquer coisa extraída deles ficam na pasta de trabalho do jogo (`$W` = `<pasta do NSP>/<título>-work`, ao lado dos NSPs no drive externo do usuário; a pasta home está quase cheia), nunca no repositório, nunca em commit, nunca impressos. Imprima apenas *nomes* de chaves e seus comprimentos.
- **Meça, depois mude.** Cada correção neste repositório partiu de uma observação concreta (um endereço de crash e sua descompilação, um censo sobre todos os shaders, um perfil de memória). Escreva a evidência no comentário de código ao lado da correção, do jeito que o código existente faz; o próximo título vai precisar dela.
- **Encontre a causa raiz; não dê apenas um contorno.** Um crash, hang ou imagem errada está encerrado quando sua causa raiz é encontrada e corrigida ali, não quando para de aparecer. Rastreie o valor errado até onde foi escrito e a chamada até a semântica que o host erra; um stub, skip, clamp, retry ou timeout que só faz o sintoma sumir é um contorno, mantido apenas quando a causa raiz não pode ser corrigida e registrado como em aberto ([AGENTS.md](../../AGENTS.md)).
- **Um repositório, um perfil por título.** O nxnative (primeiro chamado smbw-mobile) começou como uma cópia das partes genéricas do d2r-mobile. Constantes específicas do título ou do SDK vivem no perfil do jogo `dm/games/<id>/` ([dm/games/README.md](../../dm/games/README.md)). Isso cobre program ID, builds conhecidos, módulos, partição do espaço de endereços, tabelas do driver NVN, as tabelas de shaders e a identidade do app. O código lê o perfil através de `game_profile.h` (host) ou `dm/games/game.py` (ferramentas). Comportamento que serve apenas ao código de um título é condicionado pelo build ID daquele título (`dm_main_build()`), nunca deixado ligado para todos os títulos. Algumas coisas ainda estão embutidas no tradutor: as bases dos handles de textura / sampler e o modo de profundidade (ver [04](04-graphics.md)). O `dmsh_build.py` recusa um perfil cujas bases diferem das do tradutor.
- **Escreva comentários de código em inglês**, e comece as linhas de log que marcam algo não implementado ou errado com `[RED] `.
- **Teste onde roda.** O host do Mac (`dm/host/dmhost`) é o loop de desenvolvimento; o app do iOS reusa o mesmo código de host e de gráficos. Nunca afirme que algo funciona no iOS sem rodá-lo lá.

## Checklist para um novo título

1. Rode `scripts/build_ipa_from_nsp.py` na pasta do NSP do título. Sem perfil para o seu title ID, ele escreve `<pasta do NSP>/<title ID>_survey/survey.md`:
   - módulos e build IDs, versão do SDK e componentes, marcadores de engine e API gráfica;
   - contêineres RomFS;
   - o censo de pontos de reescrita e imports vs. hooks do host.

    Um programa ARM de 32 bits (`main.npdm` com o flag de instrução de 64 bits desligado: Pikmin 3 Deluxe, New Super Mario Bros. U Deluxe) para o levantamento com uma linha vermelha: o Apple silicon não executa código ARM de 32 bits, e a abordagem de execução nativa não tem tradutor para ele. A mesma checagem para uma versão de 32 bits de um jogo que tem perfil (Mario Kart 8 Deluxe 1.0.0, reportado em LNPANDY/NX2Apple#116) logo após a extração, nomeando as versões registradas para empacotar em vez dela.

    Ele extrai apenas os módulos de código mais uma lista da RomFS para o levantamento. Salvo com `--survey-only`, escreve então um perfil provisório em `<pasta do NSP>/<title ID>_build/profile/<title ID>/`, extrai o jogo, dá boot no Mac até o pedido de heap quando há memória de endereço virtual (o heap check) e empacota um IPA de melhor esforço. Esse perfil é o ponto de partida do passo 3: as chaves estáticas seguem regras verificadas contra todos os perfis, o resto é palpite ou default ([dm/games/README.md](../../dm/games/README.md)); as chaves de tempo de execução (`render_cond`, `tex_flush_upload`, `core_preempt`, …) são do bring-up encontrar. Para corridas no Mac, exporte `DM_GAMES_DIR=<pasta do NSP>/<title ID>_build/profile` até o perfil entrar em `dm/games/`.
2. Extraia a base (e o update, se no escopo) — [01](01-extract.md). Termine o levantamento — [02](02-survey.md). Anote: versão do SDK, versão da API NVN, lista de módulos, imports que faltam ao host, SVCs, censo de instruções, padrão do loader NVN, contêineres de shaders.
3. Adicione um perfil de jogo `dm/games/<title ID>/game.tsv`, nomeado pelo title ID do jogo base (parta do `game.tsv` de um perfil mantido, como `040074A01BF12000/game.tsv`: identidade, linhas `build`, `modules`; mantenha os valores de memória / NVN até serem medidos) e construa o host para ele com `make -C dm/host GAME=<id>`.
4. Rode o rewriter e confira suas contagens contra o `insn_census.py`.
5. Dê boot no Mac e itere ([03](03-bringup.md)) até o jogo alcançar seu frame loop: consulte cada falha no [índice de sintomas](symptoms.md), que leva à sua entrada nas [referências por subsistema](../reference/README.md).
6. Extraia e traduza os shaders, encontre o layout de binding pelo censo, e consiga o primeiro frame — [04](04-graphics.md).
7. Meça a memória ao longo de um minuto de execução (`footprint`, a linha de relatório de memória do host); corrija o crescimento antes de seguir.
8. Input, áudio, depois o bundle do iOS (o `dm/ios` do d2r-mobile, RomFS dentro do app).
9. Teste no telefone: um IPA não assinado que o usuário sideloada, switches através do `env.txt`, resultados através do `Documents/log.txt` ([05](05-debugging.md)). Vários bugs só apareceram lá (o [byte do command-buffer](../reference/nvn-objects.md#inlined-sdk-code-writes-into-nvncommandbuffer-0x10) e o [tamanho do buffer de áudio](../reference/audio.md#remoteios-default-io-buffer-duration)), falhas de link de pipeline em fases posteriores em [04](04-graphics.md).
10. Para um update de jogo: extraia-o sobre o jogo base, compare os imports, carregue os endereços por build, e reconstrua as tabelas de shaders para as duas versões ([01](01-extract.md)).
