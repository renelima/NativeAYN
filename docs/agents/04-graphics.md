# 04 — Gráficos: NVN sobre Metal para um título novo

A camada de gráficos registra os comandos NVN no seu próprio formato de comandos (`dm/gfx/nvn/hle_nvn.c`) e os reproduz como Metal 4 no momento do submit (`nvn_mtl.m`). Shaders nunca são traduzidos em tempo de execução: os binários de shader Maxwell originais são traduzidos offline (tradutor do Ryujinx → SPIR-V → spirv-cross → metallib) e procurados por chave. Veja `dm/gfx/README.md` para o pipeline completo; esta página lista o que muda por título.

## 1. Ache todo contêiner de shaders

Não pare no arquivo óbvio. Em Mario, o `bfsha` principal guardava 4.888 dos 12.811 shaders que o jogo realmente usa.

`dm/gfx/tools/shader_split.py <RomFS> <ExeFS main> <pkg dir> <map out> <facts out> [<pairs out>]` varre **todo** arquivo do RomFS (descomprimido de zstd, SARC expandido recursivamente) e o `main`, e reconhece os contêineres listados por engine em [reference/shaders.md](../reference/shaders.md#containers-by-engine). A tabela de pares lista as (chave de vertex, chave de pixel) de cada variação BNSH ou programa Unity. Shaders Unity precisam de uma segunda passada: arquivos cujas árvores de tipo estão faltando são varridos de novo uma vez que os bundles tenham fornecido a árvore `Shader` (ou com a que o `unityfs.py` escreveu para aquele hash, quando nenhum bundle a tem). Para um jogo base mais um update, dê RomFS e `main` como listas separadas por vírgula, base primeiro: as chaves são hashes de conteúdo, então a saída é a união das duas versões e uma build de shaders serve às duas (Mario 1.2.1 recompilou 3.451 dos seus pixel shaders; linhas v0 mantêm seus índices de pacote).

Valide a cobertura de um título novo em tempo de execução: `DM_NVN_SHDUMP=<dir>` faz o host despejar a seção de controle e o código de todo programa que ele não encontra no map; o host cria o diretório se faltar; procure esses bytes nos arquivos do jogo para achar o contêiner que foi perdido.

## 2. Indexe shaders por seção de controle + código

A chave do host é `sha256(control[0:0x880] + code)[:16]` (`prog_get` em `nvn_mtl.m`, `shader_split.py`). D2R era indexado só pela seção de controle; em Mario, 6.367 pares de shaders compartilham uma seção de controle mas diferem no código. Um comprimento ou layout de código diferente num título novo tem que se refletir nos dois lugares.

## 3. Ache o layout de bindings por censo

O driver NVN põe suas tabelas de bindings em bancos de constantes do driver. Todo jogo até aqui, drivers NVN 53 e 55 dos SDKs 6 a 21, tem o layout abaixo, que o `dmsh_build.py` decodifica e o `nvn_mtl.m` preenche em tempo de execução. Confira um jogo novo contra ele com um censo do que os shaders traduzidos dele referenciam (só o tradutor leva segundos) em vez de assumir.

| Binding | Onde | Como foi medido |
|---|---|---|
| Handles de textura combinados (`nvnCommandBufferBindTexture`) | **`c2[0x20 + 8 × slot]`**, 32 slots; a palavra de um slot mais alto fica na tabela de imagens | Mario: handles imediatos de todas as instruções TEX, 0x20…0xF0 em passos de 8. Hades II vincula o slot 34 (0x130) e nenhuma image |
| Handles de image | `c2[0x120 + 8 × slot]`, 8 slots | compute shaders da agl: 0x120 / 0x128 / 0x130 |
| Texturas separadas (`BindSeparateTexture(s)`) | `c2[0x168 + 8 × slot]`, 128 slots: os slots de textura do host 128 + n (`NVN_SEPTEX_SLOT0`) | Engage (Unity vincula só texturas e samplers separados): os nomes de textura do tradutor (`fp_t_cb<slots>_<handle>`, empacotamento `TextureHandle` do Ryujinx) dão a palavra 0x5A = 0x168 para a textura e 0x15A = 0x568 para o sampler. D2R (NVN 53) tinha o mesmo |
| Samplers separados | `c2[0x568 + 8 × slot]`, 128 slots | como acima |
| Uniform buffers | `c[3 + slot]` | |
| Storage buffers | `c0[base + 16 × slot]`, base vs 0x110 / cs 0x310 / ps 0x510 | |
| Maior point size | `c0 + 0x610` | Super Mario Odyssey (SDK 7): GLSLC limita um `gl_PointSize` escrito pelo shader a ele (`alPointSpriteShader`: `min(size, c0[0x610])`). Não é o valor do `SetPointSize`, que o jogo deixa em 1. O host escreve 2047 ali para os stages de gráficos |

Ace Attorney Investigations Collection (Unity 2022.3, SDK 17.5.3) vincula texturas e samplers separados como Engage: todos os 4.950 shaders traduzíveis decodificam todo binding (`shaders with a binding whose slot was not decoded 0`), e 190 leem linhas de `c2` como dados.

Metroid Dread (SDK 11.4.3) usa o layout de handles de textura do Mario, `0x20 + 8 × slot`: os imediatos de handles `TEX` / `TEXS` no próprio texto SASS dos arquivos de shader dele são palavras 0x8–0x22 em passos de 2. A build completa dele não deixa bindings não resolvidos nem leituras de banco de driver não preenchíveis; as outras linhas não foram medidas separadamente.

Hades II (SDK 19.3.9) vincula texturas combinadas em slots fixos, esparsos, até 34 (`fp_t_tcb_4C`: palavra 0x4C de c2 = 0x20 + 8 × 34, em `SceneFade.frag`). Com uma tabela de 32 slots, o `dmsh_build.py` reportava esse binding como não decodificado ("shaders with a binding whose slot was not decoded 1", que imprime uma linha vermelha quando o shader carrega). A tabela combinada agora vai até as texturas separadas em 0x168 (41 slots); depois do slot 31 ela divide suas palavras com a tabela de imagens, e o replay escreve uma textura vinculada ali quando o slot de image está desvinculado. O censo dos nomes `fp_t_*` nas libraries traduzidas dá os slots em uso.

Monster Hunter Rise (RE Engine, SDK 11.4.3) usa as duas tabelas ao mesmo tempo: handles combinados de `nvnCommandBufferBindTexture` em `0x20 + 8 × slot` e texturas separadas de `BindSeparateTexture(s)` em `0x168 + 8 × slot`, com samplers separados em 0x568, e vincula o slot 0 de ambas nos mesmos frames. Um censo dos nomes de textura de 23.478 shaders traduzidos: 33.813 combinados (`fp_t_tcb_1E`), 29.342 texturas separadas com um ID de sampler constante (tipo de handle 3, `fp_t_cb65538_3041005C`: textura na palavra 0x5C de c2, sampler 0x104 ORado), 8.265 textura separada + sampler separado (tipo 1, `fp_t_cb196610_1017815A`), 5.227 texturas separadas cujo próprio handle carrega o sampler (`fp_t_tcb_5A`), uns 1.500 handles de uniform buffer com um sampler constante (`fp_t_cb65541_30410028`), e 121 handles totalmente dinâmicos (tipo 4, `fp_t2d_cb0_40000000`, não suportados). Vinculações separadas vão para os slots 128 + n da tabela do host e seus handles decodificam para 128 + n, como em todo jogo; um sampler constante é o tipo de binding `samp_id` (`NVN_RB_SAMPI`, reg = o ID do sampler).

O `dmsh_build.py` decodifica os bindings com este layout (`decode_tex`), o `Program.cs` numera os slots do mesmo jeito quando procura os tipos de textura / image por slot na tabela de facts, e a camada de replay preenche os bancos de driver com ele: as tabelas combinada, de imagens, de texturas separadas e de samplers separados de `c2` (`NVN_RB_DRV2` em `encode_args`). Alguns shaders leem linhas de `c2` como dados em tempo de execução (Engage: 243, os handles de textura e sampler dos slots 0–11); a build lista leituras fora dessas tabelas como `cannot fill`. Depois de uma build completa, o resumo tem que dizer `shaders with a binding whose slot was not decoded 0`.

## 4. Texturas bindless

Os shaders de Mario leem 38 % das suas texturas através de handles guardados nos uniform buffers do próprio jogo (`fp_t_cb7_2A` = handle na palavra 0x2A de c[7] = slot uniform 4). Estes viraram os tipos de binding `tex_ubo` / `samp_ubo` (`NVN_RB_TEXU` / `NVN_RB_SAMPU`): no replay o host lê a palavra de 32 bits do uniform buffer vinculado (20 bits baixos ID de textura, 12 altos ID de sampler).

Consequência: qualquer otimização que infira "quais texturas um draw lê" a partir de slots vinculados está errada para esses shaders. As otimizações TBDR (elisão de store / load, fusão de passes) estão portanto desligadas por padrão neste repositório (`tbdr_on()`, `DM_NVN_TBDR=1` para ligar).

## 5. Convenção de profundidade

`nvnDeviceSetDepthMode` near = −w (GL, z em [−w, w], o padrão do NVN) versus near = 0 (D3D / Metal, z em [0, w]). O Metal recorta qualquer coisa com z < 0, então os vertex shaders de um jogo em modo GL têm que terminar com z' = z/2 + w/2. O modo é estado de execução, e os jogos diferem: Mario, Metroid Dread, Super Mario 3D World e Breath of the Wild mantêm GL; Link's Awakening, 13 Sentinels e Engage põem near = 0.

Então o tradutor deixa o z em paz (`QueryGraphicsState` depth mode false em `Program.cs`), e o `dmsh_build.py` (`vs_depth`) escreve dois entry points em toda vertex library: `main0` com a reescrita GL (a mesma aritmética que o Ryujinx emitia) e `main0_z` sem ela (reflection `entry_z`). O host escolhe um quando carrega um vertex shader, pelo modo que o jogo pôs (`mtl_set_depth_zero`, `shader_load` em `nvn_mtl.m`). Um jogo novo não precisa de ajuste nenhum; se um jogo mudasse o seu modo depois de os vertex shaders serem carregados, uma linha vermelha diz isso.

- Reescrever um jogo near = 0 para GL ainda desenha corretamente (os testes de profundidade mantêm a sua ordem), mas toda profundidade cai em 0.5..1, então efeitos que transformam a profundidade de volta em distância ficam errados: a profundidade de campo externa de Link's Awakening borrava a tela inteira.
- Não reescrever um jogo GL: a cópia de tela inteira para a janela é recortada, então a janela fica preta mesmo com um fragment shader de cor sólida.
- Function constants do Metal também poderiam escolher a variante, mas qualquer função com uma function constant tem que ser especializada antes de um pipeline poder usá-la (medido: uns 2,4 ms por vertex shader num M4 Pro); o segundo entry point só custa tempo de build e uns 30 % a mais de tamanho de library.

Desligado no modo TBDR. A linha `residency set` conta clears tomados por um pass posterior e os que caíram sozinhos |
| `DM_NVN_FLUSH_FILL=0` | Uma textura de GPU nova num pool que a CPU pode escrever começa como zeros, como antes. Por padrão uma cujo storage o jogo deu flush (`nvnMemoryPoolFlushMappedRange`) antes do primeiro uso é preenchida a partir daquele storage uma vez (linhas `initial content: … flushed by the CPU before its first use`; as tabelas de céu do Breath of the Wild) |
| `DM_NVN_BARRIER=game` / `full` / `ab` | Como os passes de draw são ordenados (`ab`: alternando com as fases do `DM_AB`). `full` (padrão): todo pass espera todo trabalho de GPU anterior. `game`: um pass espera só pelo stage de fragmento do pass anterior, então o trabalho de vértice dele se sobrepõe aos fragmentos do pass anterior, a menos que o jogo tenha chamado `nvnCommandBufferBarrier` no meio ou um compute / cópia / upload tenha rodado (esses mantêm barreiras completas). Só leituras de stage de vértice da saída do pass anterior sem barreira do jogo mudam a ordem |
| `DM_NVN_GPU_TS=segment` / `submission` | O que os timestamp reports gravam, em vez do `gpu_timestamps` do profile: o início / fim de GPU do segmento que guarda cada report, ou um tempo para a submissão inteira |
| `DM_NVN_DISPATCH_OWN=1` | Todo dispatch de compute num compute encoder próprio com barreiras completas, como antes (por padrão os dispatches dividem o copy encoder, `dispatch_enc`) |
| `DM_NVN_VCONV_CPU=1` | Entradas de vértice inteiras alimentadas com formatos de outra classe são convertidas na CPU, como antes (por padrão a library `<key>_bv` do shader as pega por entradas sombra, `vin_on`) |
| `DM_NVN_GPUPROF=f`, `f1-f2` or `every:n` | Início e duração de GPU de todo encoder daqueles frames (`every:n`: os frames que são múltiplos de n, para um celular), a partir dos timestamps do counter heap do Metal 4 (linhas `[gpuprof]`: tipo, tamanho, attachments, draws, segmento de command-buffer, KB de load / store de attachment, formatos pixel Metal da cor 0 e da profundidade; uma linha `frame` com o tempo de render e de compute / cópia, o tráfego de attachments e o intervalo do primeiro início ao último fim). O `dm/tools/gpuprof.py` os soma por forma de pass ([05](05-debugging.md#tempo-de-gpu-no-dispositivo)) |
| `DM_AB=<frames>` | Os conjuntos postos em `ab` alternam em fases de tantos frames, num único processo e cena; uma linha `[ab]` por fase com GPU e tempo de frame e tráfego de attachments ([05](05-debugging.md#tempo-de-gpu-no-dispositivo)) |
| `DM_GPU_CAPTURE=f[:n]` or `gpu:<ms>[:<after>]` | Um trace de GPU Metal daqueles frames para o Metal debugger do Xcode, em `gpu_captures/` do diretório de trabalho ([05](05-debugging.md#tempo-de-gpu-no-dispositivo)) |
| `DM_NVN_ENC_THREAD=1` | Codificação Metal numa thread própria: a thread de submit registra as chamadas de encoder e um trabalhador as reproduz (`nvn_rec.h`); ligado por padrão no iOS (`DM_NVN_ENC_THREAD=0` desliga), desligado no macOS |
| `DM_NVN_UB_LAZY=n` | Os updates de uniform inline adiados mantidos através de um fim de render pass (padrão 160): eles chegam antes da próxima cópia, de um draw ou dispatch que leia a memória deles de outro jeito que não por bindings de uniform que as sombras cobrem (`ubd_conflict`, `ubd_conflict_cs`), um draw de transform feedback, ou o fim da submissão, em vez de a cada fim de pass; 0 os faz chegar a cada fim de pass, como antes |
| `DM_NVN_UB_COPY_THREAD=0` | Sombras de uniform de 512 bytes ou mais são copiadas na thread de submit, como antes (por padrão um trabalhador as copia) |
| `MTL_DEBUG_LAYER=1 MTL_DEBUG_LAYER_ERROR_MODE=nslog` | Validação Metal sem abortar |
